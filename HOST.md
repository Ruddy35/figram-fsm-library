# Контракт хоста

Движок — чистая функция: снимок и событие на входе, новый снимок и действия
на выходе. Всё, что связано с базой, сетью и временем, делает хост — код
разработчика вокруг движка. Ниже правила, при которых бот ведёт себя так,
как нарисовал дизайнер, даже при сбоях, повторах и параллельной нагрузке.

Эталонная реализация и её проверка — `ffi/python-example/host_sim.py`.

## 1. Обработка события

Для каждого обновления Telegram (у него есть `update_id`):

1. **По одному на пользователя.** События одного пользователя обрабатываются
   строго последовательно: блокировка или очередь на пользователя. Разные
   пользователи — параллельно. Без этого два события прочитают один снимок,
   и одно из обновлений потеряется.
2. **Отсев повторов.** Если `update_id` уже обработан для этого пользователя,
   событие пропускается. Обработанные `update_id` записываются в той же
   транзакции, что и снимок (шаг 4), в отдельную таблицу «пользователь,
   `update_id`» с индексом, а не множеством внутри строки снимка (оно растёт с
   каждым событием). Хранить достаточно окно повторной доставки: Telegram
   держит неподтверждённые обновления не дольше 24 часов; события таймеров —
   до срабатывания или отмены таймера.
3. **Шаг.** Хост читает снимок, вызывает `step`. Если движок ответил `need`,
   хост вычисляет условия и повторяет `step` с `guards`. Условия вычисляются
   по данным, где **уже применены все действия `call`, зафиксированные
   предыдущими шагами этого пользователя** (и не применены действия текущего
   шага). Действия исполняет отдельный исполнитель (раздел 2), поэтому перед
   шагом дождитесь исполнения незавершённых действий пользователя из outbox
   (барьер на пользователя) — либо исполняйте вызовы, меняющие данные, которые
   читают условия, в той же транзакции, что и снимок. Иначе, например,
   `cart_not_empty` после «Добавить» прочитает пустую корзину, а проверка
   баланса дважды разрешит покупку на одни деньги. Условия могут зависеть и от
   данных самого события (текст сообщения, payload кнопки).
4. **Атомарная запись.** Одной транзакцией сохраняются: новый снимок,
   отметка «`update_id` обработан» и действия ответа в очередь исходящих
   (outbox), каждое с ключом `пользователь:seq:номер`. `seq` берётся из
   нового снимка, номер — позиция действия в ответе. Ключ уникален, только
   пока `seq` пользователя не повторяется: не начинайте существующего
   пользователя через `start` (раздел 4).
5. **Подтверждение.** Только после фиксации транзакции хост подтверждает
   обновление Telegram. Сбой до фиксации — Telegram доставит обновление
   повторно, и оно обработается как в первый раз. Webhook: подтверждение —
   ответ 2xx на запрос этого обновления. getUpdates: подтверждение
   накопительное — вызов с `offset` подтверждает **все** обновления с меньшим
   `update_id`, в том числе ещё не обработанные обновления других
   пользователей; поэтому сначала запишите полученные обновления во входящую
   очередь в базе и только потом запрашивайте следующий `offset`
   (обрабатывайте из очереди), либо подтверждайте только до наименьшего
   незавершённого `update_id`.

## 2. Исполнение действий

Отдельный исполнитель забирает действия из outbox по порядку и после
выполнения помечает их выполненными.

* **Идемпотентность.** Действие может выполниться повторно (сбой между
  выполнением и отметкой), поэтому внешние вызовы передают ключ действия как
  ключ идемпотентности: CRM, платёжный сервис, собственная база с
  уникальным индексом. Так `create_order` выполняется один раз, сколько бы
  раз исполнитель ни перезапускался.
* **Порядок.** Действия одного пользователя выполняются строго в порядке
  фиксации — по `seq`, внутри ответа по номеру (отмена таймеров, действия
  стрелки, запуск таймеров, отправка сообщения), в том числе действия разных
  ответов. Действия разных пользователей независимы: несколько исполнителей —
  только с разбиением очереди по пользователю. Иначе запуск таймера прошлого
  шага может выполниться после отмены или нового запуска, и напоминание
  потеряется.
* **Данные события.** Если действию нужны данные события (`save_address` —
  текст сообщения), сохраните их вместе с действием в той же транзакции.
* **Отказы.** Постоянный отказ внешней системы не должен останавливать
  исполнение для остальных пользователей: после нескольких попыток действие
  уходит в отдельную очередь отказов с оповещением, очередь этого
  пользователя ждёт решения.
* **Срок таймера** отсчитывайте от фиксации шага (сохраните время в outbox),
  а не от момента, когда исполнитель дошёл до `start_timer`.
* **send** — отправка сообщения пользователю, «хотя бы один раз». Повторная
  отправка после сбоя видна пользователю; хранение `message_id` по ключу
  действия сужает окно, но не закрывает его: сбой между ответом Telegram и
  записью `message_id` всё равно даст повтор.

## 3. Таймеры

* `start_timer` приходит с жетоном. Хост планирует событие
  `{"event": "timer:<имя>", "token": <жетон>}` через `ms` миллисекунд
  и хранит запланированное по паре «пользователь, имя».
* `cancel_timer` снимает запланированное событие, если оно ещё не ушло.
* Если событие уже в пути и отменить его нельзя — ничего страшного: движок
  примет срабатывание только с жетоном текущего запуска, устаревшее он
  проигнорирует. Поэтому отмена — оптимизация, а не условие корректности.
* Событие таймера проходит тот же путь, что и обновление Telegram (раздел 1);
  в качестве `update_id` используйте `timer:<имя>:<жетон>`.

## 4. Сброс пользователя

Чтобы начать пользователя заново (команда поддержки, «удалить мои данные» с
сохранением аккаунта), используйте `restart` с **последним зафиксированным**
снимком (прочитанным под блокировкой пользователя, раздел 1), а не `start`.
`restart` отменяет старые таймеры и продолжает счётчик `seq`, поэтому жетоны
новых таймеров не совпадут с жетонами запоздавших старых событий, а ключи
новых действий `пользователь:seq:номер` — с ключами уже выполненных.

Снимок из реплики с отставанием или из резервной копии для `restart` не
годится: движок не отменит таймеры, запущенные после этого снимка, и повторно
выдаст уже использованные `seq`. Запоздавшее событие такого таймера может
совпасть по жетону с новым и будет принято, а новые действия получат ключи
старых и будут отброшены как повторы.

`start` (счётчик с нуля) — только для пользователя, у которого ещё не было ни
одного действия. После `start` ключи `пользователь:1:0`, `пользователь:2:0`, …
совпадают с ключами прошлых действий: CRM, платёжный сервис или outbox с
уникальным ключом молча отбросят новые действия как повторы — например,
`create_order` и `save_address` второго заказа, пройденного тем же путём, не
выполнятся, хотя пользователь увидит «заказ принят».

Если снимок утерян или удалён, храните отдельно от него «верхнюю отметку» —
наибольший `seq`, выданный пользователю (одно число, не персональные данные;
его можно восстановить как максимум `seq` в ключах outbox), и начинайте
пользователя через `restart` со снимком-заглушкой:

```
{"id": 1, "op": "restart", "snapshot": {"at": "-", "seq": N}}
```

где `N` — верхняя отметка. Сообщения `-` в документе нет, движок начнёт
пользователя с начального сообщения, а счётчик продолжится с `N + 1`. Перед
этим снимите у планировщика все таймеры пользователя: заглушка не знает их
имён.

## 5. Сбои движка

Клиент (`figram_client.py`) завершает ожидающие запросы ошибкой при любом
нарушении протокола: невалидный JSON, неизвестный или отсутствующий `id`,
обрыв вывода, падение процесса, отсутствие ответа за таймаут. Неисправный
процесс останавливается и при следующем запросе заменяется новым. Запросы,
завершённые такой ошибкой, хост повторяет по правилам раздела 1: шаг движка —
чистая функция, повтор безопасен, пока транзакция не зафиксирована.
Ответ движка `{"error": ...}` (снимок отвергнут, `seq_overflow`) детерминирован:
повтор даст ту же ошибку, поэтому такое событие уходит в очередь отказов с
оповещением, а не повторяется бесконечно.

Загрузка документа идёт до первого ответа процесса и на больших документах
занимает секунды и минуты (несколько тысяч сообщений, глубокая вложенность,
много разделов с «вернуться туда, где был»): ждите ответа на `hello` с
отдельным таймаутом, не меньше времени загрузки, иначе процесс будет
заменяться, не успев загрузиться.

## 6. Обновление документа бота

* Новую версию документа загружайте в движок целиком; снимки пользователей
  не мигрируют.
* Если сообщения из снимка больше нет, движок начинает пользователя заново
  и отвечает `"recovered": true` — его стоит логировать.
* Если запомненного места больше нет, «вернуться туда, где был» ведёт на
  начальное сообщение раздела.
* Снимок с неизвестным полем или версией движок отвергает: значит, его записал
  более новый движок, и откатывать движок без отката снимков нельзя.
* Сообщение, ставшее разделом, тоже считается исчезнувшим: пользователь
  начинает с начального сообщения бота (`"recovered": true`), а не раздела.
  Запомненное место, перенесённое в другой раздел, считается исчезнувшим.
* Таймеры снимка не мигрируют. Если у текущего сообщения пользователя в новой
  версии таймер переименован, удалён или перенесён на другое сообщение, при
  уходе движок отменяет таймеры этого сообщения по **новой** версии: старый
  таймер не отменяется, его запись остаётся в `timers` снимка, а уже
  запланированное событие `timer:<старое имя>` будет принято (жетон
  совпадает). Если стрелка по этому событию есть у раздела выше, она
  сработает, хотя пользователь уже не на том месте, где таймер запускался.
  Таймер новой версии на текущем сообщении запустится только при следующем
  входе в него. Перед выкладкой такой версии снимите у планировщика события
  таймеров, которых в новой версии нет на текущих сообщениях пользователей,
  либо выполните для затронутых пользователей `restart` (раздел 4).
* Переименованные условия и действия: хост, собранный под старую версию,
  передаст условие под старым именем — движок проигнорирует его как лишнее и
  снова ответит `need`. Хост и документ выкладываются вместе; `hello` версию
  документа не сообщает.

## 7. Что проверено

`host_sim.py` моделирует продакшен: 30 пользователей проходят заказ пиццы,
каждое событие доставляется дважды и параллельно, 16 потоков, отдельный
исполнитель outbox, сбои внедряются случайно в трёх местах (до фиксации, после
фиксации, между исполнением действия и отметкой). Условия вычисляются по
данным: корзина — по исполненным `add_to_cart`/`clear_cart`, зона доставки —
по тексту адреса; треть пользователей сначала жмёт «Оформить» с пустой
корзиной, половина вводит адрес вне зоны. Результат: каждый пользователь
пришёл туда, куда ведут его данные (`done` и ровно один заказ или `pickup`
без заказа), потерянных обновлений нет (итоговый снимок совпадает с
последовательным проигрыванием обработанных событий с теми же условиями),
невыполненных действий нет. Устаревшее событие таймера после перезапуска
игнорируется.

Контроль без барьера (`host_sim.py … --no-barrier`, условия до исполнения
действий прошлого шага) даёт неверные ветки — тест это ловит.

Контрольный прогон — хост без отсева повторов и без ключей идемпотентности —
даёт повторные заказы, то есть тест эти нарушения ловит.

`client_faults.py` проверяет клиент на шести видах сбоев движка: все запросы
из многих потоков завершаются ошибкой без зависания, процесс заменяется.
