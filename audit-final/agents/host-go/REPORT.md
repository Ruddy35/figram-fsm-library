## 1. Область и контракт

### 1.1 Что построено (`audit/host-go/`, с нуля; `ffi/go-example` и `host_sim.py` не использовались)

- `figram/` — собственный cgo-биндинг. Решения о владении, времени жизни и потоках:
  - **Инициализация.** `figram_init` не потокобезопасна (обычный `static int ready`; гонка роняет процесс — NP-04), поэтому `Init()` = `sync.Once`; ошибка кэшируется. Любой вход вызывает `Init()`.
  - **sigaltstack.** Рантайм Lean при инициализации ставит вызывающему потоку (а это M рантайма Go) свой `sigaltstack` на 14 528 байт (`stack_guard`, malloc). Биндинг сохраняет и восстанавливает его вокруг `figram_init`; `InitReport()` фиксирует, что Lean стек менял (NP-02).
  - **Потоки.** Каждый вход в C закрепляет M. Прослойка `figram_ffi.c` сама вызывает `lean_initialize_thread` для каждого нового потока ОС. Число одновременных вызовов C ограничено семафором (`SetMaxConcurrentCalls`, по умолчанию GOMAXPROCS, у хоста 4). Так ограничено и число потоков ОС, «запертых» в C.
  - **Строки.** ABI — C-строки без длины. Сырой NUL обрезал бы запрос, поэтому биндинг его отвергает (`ErrNUL`). Невалидный UTF-8 проходит, Lean заменяет его на U+FFFD (NP-03). Вход копируется в malloc-буфер и освобождается после вызова; ответ копируется в память Go и всегда освобождается `figram_free` (defer).
  - **Время жизни автомата.** `*Machine` владеет одной ссылкой из `figram_load_doc`. `Request` берёт in-flight-ссылку под мьютексом. `Close`:
    1. запрещает новые вызовы (`ErrClosed`);
    2. ждёт выхода всех текущих вызовов из C;
    3. вызывает `figram_unload` ровно один раз.

    Финализаторов нет: выгрузка только явная. Окно между чтением указателя и `lean_inc` внутри `figram_request_json` закрыто счётчиком in-flight. Без него — use-after-free: красный контроль `TestUnsafeUnloadIsRed` и вариант `unload-no-wait`, оба дают SIGSEGV в cgo.
  - **Причина отказа загрузки.** `figram_load_doc` отдаёт только NULL, поэтому биндинг вызывает `figram_check_json` (NP-06).
- `host/` — хост:
  - SQLite (WAL, `synchronous=FULL`, `busy_timeout=3000`). Таблицы: `users` (снимок, `version` для оптимистической блокировки, `doc`, постоянная верхняя отметка `hw_seq`), `processed`, `transitions` (журнал шагов, включая полный снимок), `outbox(key UNIQUE)`, `timers`, `rejected`, `host_log`, доменные таблицы по `domain.md`.
  - **Шаг.** Блокировка пользователя (мьютекс в процессе) → чтение снимка → строгая проверка снимка и `seq == hw_seq` (иначе ремонт через `restart` от `hw_seq`, domain.md §6) → `step`. При `need` применяются **G1** (синхронный дренаж своих ожидающих `call` до последнего) и **G2** (блокировка слота до фиксации, подсчёт чужих ожидающих `reserve_slot`); условия вычисляются из БД, затем повторный `step`. Затем **одна транзакция**: снимок + `processed` + `transitions` + строки outbox + `timers`. Только после неё ack.
  - **Писатель.** Все записи сериализуются мьютексом писателя внутри процесса (у SQLite и так один писатель). Без него p99 на 1000 пользователях был 750 мс, с ним 248 мс. Внешний захват БД (`db_lock`) по-прежнему даёт `SQLITE_BUSY` через 3 с, то есть NACK.
  - **Проверка ответа движка.** Строгий разбор: UTF-8, без повторяющихся ключей, `id` совпадает. Ровно один вид ответа, причём у `need`/`error` нет посторонних полей. Снимок проверяется по схеме, `at` должен быть сообщением документа. Формы действий проверяются, `ms` — задержка таймера из документа. Правила `seq`: `start` → 1, `restart` → `hw+1`, переход → `+1`, игнор → без изменения, `token` = `seq`.
  - **Ключ идемпотентности** `user:seq:index`. `seq` монотонен всю жизнь пользователя:
    - `start` — только для пользователя без строки;
    - сброс и ремонт — `restart` (со снимком или `{"at":"-","seq":hw}`);
    - `hw_seq` только растёт (MAX);
    - строки пользователей не удаляются;
    - `outbox.key UNIQUE` служит растяжкой.

    Иммунитет к ET-01 показан красным вариантом `seq-keys-start`.
  - **Исполнитель outbox.** 4 воркера, строки одного пользователя строго по порядку (блокировка outbox пользователя, общая с G1). Локальные `call` применяются в той же транзакции, что и отметка `done`. Внешние уходят в CRM-симулятор с `Idempotency-Key`. `send` — at-least-once. После успешного внешнего эффекта повторяется запись отметки, а не сам эффект (`persistAck`, до 30 с).
  - **Таймеры.** Свой планировщик на симулированных часах; часы хранятся в `meta`. `advance_to` срабатывает в порядке (due, user, name, token) через обычный путь шага, `update_id = timer:<name>:<token>`. После рестарта догоняются просроченные срабатывания.
  - **Обновление документа v1→v2.** Новый документ загружается `figram_load_doc` до любых изменений. Затем атомарно: `users.doc` и `version+1` (гоняющиеся шаги на старом документе повторяются на новом); таймеры с исчезнувшими именами помечаются `orphaned` (смягчение ET-02). Старый автомат выгружается после выхода своих вызовов из C (`Machine.Close`). Есть и `reload_doc` — перезагрузка того же документа под нагрузкой.
  - **Валидация входящих обновлений.** user `[A-Za-z0-9_-]{1,64}`; `update_id` — простое целое 0…2^53−1; событие `(cmd|btn|msg|payment):[a-z0-9_]{1,48}`; `timer:*` и `token` от Telegram запрещены; `arg` — строка ≤ 4096 символов без NUL; повторяющиеся ключи запрещены. Неизвестные дополнительные поля игнорируются (совместимость с новыми полями Telegram).
  - **Точки краха** — настоящий `kill -9` себя (`syscall.Kill(getpid, SIGKILL)`) в 4 местах:
    - `before_commit` — внутри открытой транзакции;
    - `after_commit`;
    - `before_effect`;
    - `after_effect_before_ack` — у локального `call` внутри транзакции, у внешнего — после ответа CRM/TG.

    Перед смертью хост записывает в `crashes.log` (fsync), какая точка сработала.
  - **Сбои движка `engine_fault` в FFI-отображении** — слой между биндингом и хостом:

    | режим | отображение |
    |---|---|
    | `kill` | `kill -9` хоста внутри вызова движка: падение встроенного движка = падение хоста |
    | `hang` | горутина вызова спит дольше срока 3 с до входа в C; хост бросает вызов и повторяет. Настоящее зависание внутри C прервать нельзя (поток ОС потерян), см. §5 |
    | `corrupt` | схемно-валидный, но неверный ответ: регистр первой буквы `at` |
    | `truncate`, `garbage` | половина ответа или 40 случайных байт |
    | `wrong_id` | подменённый `id` |
    | `bad_snapshot` | `{"at":"","seq":-1}` |
    | `bad_action` | неизвестное действие, в том числе рядом с `need` |

    Внедрения и обнаружения пишутся в `host_log` и переживают крах.
- `cmd/fghost` — процесс хоста: HTTP через unix-сокет. `/update` возвращает 200 (ack) или 503 (NACK) — как webhook Telegram; `/ctl` принимает управляющие команды.
- `cmd/fgrun` — прогонщик, внешний симулятор и оракул:
  - **«Telegram».** Обновления пользователя идут по одному до ack, разные пользователи — окном 32. `dup:k` доставляется параллельно, `delay_ms` соблюдается. NACK и обрыв ведут к повтору; после краха повторяется всё неподтверждённое.
  - **Супервизор.** Ждёт процесс хоста. При смерти перечитывает `crashes.log` и перезапускает хост на той же БД, передавая невыстрелившие точки через `-arm`.
  - **Внешние сбои.** Внешний процесс держит `BEGIN EXCLUSIVE` на БД хоста (`db_lock`); испорченные снимки (`corrupt_snapshot`) пишутся прямо в БД.
  - **Симулятор CRM/Telegram** живёт в процессе прогонщика (unix-сокет HTTP) и потому переживает `kill -9` хоста. Режимы: 500, 429 (`Retry-After-Ms`), `timeout` (эффект применён, соединение оборвано), `timeout_before`, `dup` (запрос применён дважды), `delay` (ответ после ms при клиентском таймауте 1 с), `reorder` (пачки до 3 запросов за 40 мс применяются в перемешанном порядке).
  - **Оракул** (`check.go`) — 23 инварианта (26 на adversarial):
    - собственная независимая модель домена, которая переигрывает действия движка из журнала переходов в порядке фиксации; код хоста не используется;
    - сравнение с эталонным прогоном того же корпуса без сбоев на исправном хосте (`clean`), для adversarial также без вредных строк (`pristine`);
    - дамп БД до и после рестарта;
    - времена смертей процесса против времён доставок.
- `scripts/run_all.sh` (15 корпусов), `scripts/red_matrix.py` (матрица RED), `compare/compare.py` (сравнение Go с Python), `cmd/fgmem`, `cmd/fgprobe`, `cmd/fgsigprobe` (нативные замеры).

Чтобы сравнение имело смысл, решения по неоднозначным местам `domain.md` я согласовал с хостом Python, прочитав его код:
- reset — через `restart` с текущим снимком;
- orphaning таймеров при обновлении документа;
- регулярные выражения валидации;
- статусы ack.

Код хоста при этом свой, а проверяемая вещь — **другой движок и другой транспорт** (встроенная библиотека вместо процесса).

### 1.2 Нормализация для сравнения Go и Python (задана до сравнения, `compare.py`)

- **N1.** `update_id` вида `reset:<x>` → `reset`: у Python это счётчик доставок, у меня номер строки корпуса.
- **N2.** Переход сравнивается по полям (`update_id`, `event`, `arg`, `token`, `kind`, `seq`, `at`, `t_ms`, `actions`, `recovered`); `actions` — как значения JSON. `t_ms` — симулированные часы, сравниваются точно.
- **N3.** Итоговый снимок сравнивается как значение JSON, плюс `doc`.
- **N4.** Эффекты: множества (key, user, CRM-операция) и (key, user, текст `send`). Дубли Telegram зависят от тайминга (at-least-once), поэтому дедуплицируются по ключу.
- **N5.** booking: победитель гонки за дефицитный слот зависит от тайминга (shared/README). Расхождения допустимы только у участников конкурирующих блоков (≥2 подтверждения одного слота между барьерами). При этом должны совпасть инвариантные к победителю агрегаты:
  - мультимножество итоговых `at`;
  - активные брони по слотам;
  - число переходов;
  - эффекты по операциям.
- **N6.** NACK, повторы, дубли Telegram и латентность только печатаются и не сравниваются.

- **HP-06 (python).** Ошибки движка — свободный текст. Мой хост не ищет подстроку «снимок»: снимок строго проверяется до вызова движка, а ошибку движка на валидный запрос он поглощает со статусом `error`.
- **FC-03.** Невалидный UTF-8 → U+FFFD: тот же механизм в FFI (NP-03).
- **ET-07.** Вложенность больше 256: через FFI на потоке cgo — ошибка без переполнения стека даже при 100 000 уровнях (fgprobe).

### Собственные дефекты моего хоста и стенда, найденные своими тестами и исправленные (не продукт, для полноты)

- Строгая проверка `snapshot.timers` по документу → NP-05 (оставлена как вариант `strict-snapshot-timers`).
- `bad_action` рядом с `need` проходил валидатор (поле `actions` разрешалось при `need`). Нашёл `engine_faults_effective`: `bad_action_undetected` = 1. Теперь у `need`/`error` нет посторонних полей.
- Раннее подтверждение по HTTP с chunked-кодированием не доходило до клиента при `kill -9`, и вариант ack-before-commit не краснел. Теперь `Content-Length`.
- `UNIQUE(user,name,token)` у `timers` превращал путь ET-01 в «ядовитое» обновление и маскировал timer_not_early в RED-варианте. Снят; растяжкой служит `outbox.key`.
- Без мьютекса писателя busy-handler SQLite давал p99 750 мс на 1000 пользователях; с ним 248 мс.
- Оракул send_duplicates_explained сначала не учитывал запрос, принятый симулятором до `kill -9` и применённый после (`reorder`). Теперь сравнивается время прихода запроса.
- Неверная проверка ёмкости в `reserve_slot` (`errors.Is` по перезаписанной ошибке).

## 5. Что не проверено и остаточный риск

- **Настоящее зависание внутри C.** Не воспроизводилось: в рабочем движке зависания нет. `hang` отображён как зависание горутины до входа в C. Вызов cgo нельзя прервать: поток ОС и слот семафора будут потеряны. Защита — только сторожевой перезапуск процесса; он не реализован, лишь описан.
- **TSan/ASan процесса Go с библиотекой** не запускались. Оркестратор гонял C-харнесс с ASan/UBSan (LOGS/35-*). `-race` видит только код Go.
- **Хост из нескольких процессов на одной БД** не испытан: оптимистическая `version` есть, но мьютекс писателя действует внутри одного процесса.
- **Одновременный `figram_init`** в Go-хосте закрыт `sync.Once`; C-репро — NP-04.
- **Сбой ОС и потеря питания** не моделировались: моделируется только `kill -9` процесса. Soak шёл с `synchronous=NORMAL`.
- **Независимость реализаций частичная.** Неоднозначности `domain.md` я согласовал с хостом Python, прочитав его код (§1.1), и оракул домена тоже написан мной по `domain.md`. Ошибка понимания, общая для обоих хостов, не будет видна. Движок и транспорт при этом разные — это и есть проверяемая вещь.
- **Масштабирование движка на одном общем MT-автомате против отдельного автомата на горутину** (LOGS/n02b): 23,0 → 16,9 → 12,6 мкс/оп при `-cpu 1, 2, 4` против 25,6 → 15,3 → 11,6. Разница ≤ 10 % при load avg 4–5 на 4 ядрах — в пределах шума. Доказательств конкуренции за атомарные счётчики общего объекта нет, но на общей машине точнее не измерить.
- **Сравнение с Python** — по одному прогону каждого хоста. Победители booking и дубли Telegram от прогона к прогону меняются (это допустимо).
- Не утверждаю, что ошибок больше нет. Покрытие: 15 корпусов, 25 RED-прогонов, все 26 инвариантов видели красными, 17 модульных тестов (-race; 16 и контроль), soak 11 мин.
