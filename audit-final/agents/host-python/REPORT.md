## 1. Область и контракт

**Что построено.** Самостоятельный хост `audit/host-python/` (только stdlib + sqlite3). Код из `host_sim.py` и `go-example` не переиспользовался.

- **Транспорт движка — собственный** (`engine_transport.py`). Устроен так:
  - процессы `figram-engine`, на каждый документ пул из K процессов; пользователь всегда попадает в один процесс (crc32);
  - строгая проверка каждого ответа: id, взаимоисключающие виды ответа, схема снимка, формы действий;
  - при EOF/EPIPE/таймауте/нарушении протокола процесс убивается и пересоздаётся, шаг повторяется.
  - `figram_client.py` **не использовался** и интеграцией под тестом не является.
- **SQLite (WAL, synchronous=FULL по умолчанию).** Таблицы:
  - `users` (снимок, `version` для оптимистической блокировки, `doc`, постоянная верхняя отметка `hw_seq`);
  - `processed` (user, update_id), `transitions` (журнал шагов), `outbox` (`key UNIQUE`), `timers`;
  - доменные таблицы. Журнал внешнего симулятора лежит в отдельной `ext.sqlite`.
- **Шаг.** Выполняется под блокировкой пользователя; при фиксации дополнительно проверяется `version`. Последовательность:
  1. прочитать снимок;
  2. `step`;
  3. при `need`: правило G1 (исполнить свои ожидающие `call`), затем правило G2 (блокировка ресурса), затем условия из доменной БД;
  4. повторный `step`;
  5. **одна транзакция**: снимок + processed + transitions + строки outbox + таблица timers;
  6. только после этого ack.
- **Ключ идемпотентности** `user:seq:index`. Иммунитет к ET-01 обеспечивают три меры:
  - `start` вызывается только для пользователя без строки в `users`;
  - сброс и ремонт делаются через `restart` с `{"at":"-","seq":hw_seq}`;
  - `outbox.key UNIQUE` работает как растяжка: коллизия обрывает транзакцию, тихой дедупликации нет.
- **Исполнитель outbox** — 4 потока; строки одного пользователя строго по порядку (блокировка outbox пользователя).
  - Локальные `call` применяются в той же транзакции, что и отметка «done».
  - Внешние `call` уходят в CRM-симулятор с ключом.
  - `send` уходит в Telegram-симулятор без ключа.
  - После успешного внешнего эффекта хост повторяет запись отметки до 30 с, а не сам эффект (`persist_ack`).
- **Таймеры.** Свой планировщик на симулированных часах, хранится в БД; update_id срабатывания — `timer:<имя>:<жетон>`. После рестарта догоняет просроченные срабатывания.
- **Обновление документа.** Новый документ загружается в движок; запланированные таймеры, имён которых нет в новом документе, отменяются (смягчение ET-02).
- **Испорченный снимок.** Невалиден по схеме или `seq ≠ hw_seq` → ремонт через `restart` от `hw_seq` плюс отмена всех таймеров пользователя.
- **Входящие обновления валидируются:**
  - user `[A-Za-z0-9_-]{1,64}`, update_id — целое 0…2^53−1;
  - событие `(cmd|btn|msg|payment):…`; `timer:*` и `token` от Telegram запрещены;
  - arg ≤ 4096 символов, без NUL;
  - JSON с повторяющимися ключами отвергается.

**Правила для условий** (нормативно описаны в `hosts/shared/domain.md`):
- **G1.** Перед вычислением условий пользователя U хост исполняет префикс его outbox до последнего ожидающего `call`. При временном сбое шаг не фиксируется и не подтверждается.
- **G2.** `slot_free` вычисляется под блокировкой слота, которая держится до фиксации, и учитывает зафиксированные, но ещё не исполненные `reserve_slot` других пользователей.

**Испытательный стенд.**
- `runner.py` играет роль «Telegram»: повторяет доставку до ack, после краха повторно доставляет неподтверждённое. Он же оператор и источник сбоев.
- Сбои реальные:
  - kill -9 (`os.kill(getpid(), SIGKILL)`) в 4 точках и перезапуск с той же БД; невыстрелившие точки заново взводятся после рестарта;
  - внешний процесс держит `BEGIN EXCLUSIVE` на БД хоста;
  - отдельный процесс-прокси `evil_proxy.py` между хостом и настоящим движком портит ответы;
  - SIGKILL процесса движка;
  - CRM/TG-симулятор с режимами 500/429/timeout/timeout_before/dup/delay/reorder;
  - испорченные снимки записываются прямо в БД.
- `checker.py` — независимый оракул:
  - собственная модель домена, которая переигрывает действия движка в порядке фиксации (код условий хоста не используется);
  - эталон — тот же корпус без строк-сбоев на **исправном** хосте; для adversarial дополнительно «чистый» эталон без вредных строк.

**Общие артефакты** (я их владелец): `/home/user/figram-audit/hosts/shared/` — `bots/` (pizza, pizza.v2, booking, support, support.v2, reminders, reminders.v2), `domain.md`, `README.md` (форматы), `corpus/` (15 файлов). Заморожены файлом `VERSION` с SHA-256; проверка `python3 audit/host-python/freeze_shared.py --check` → `ok: 24 shared files match VERSION` (LOGS/freeze-check.log). `figram check` на всех 7 ботах — код 0 (LOGS/figram-check-*.log); негативный контроль (битая стрелка) — код 1 (LOGS/figram-check-NEGATIVE-booking-broken.log).

## 4. Что не проверено и остаточный риск

- Параллельная доставка разных обновлений одного пользователя (Telegram webhook с max_connections>1): прогонщик сохраняет порядок по пользователю.
- Хост из нескольких процессов (оптимистическая `version` есть, но не испытана).
- Сбой ОС и потеря питания: моделируется только kill -9 процесса; NORMAL против FULL на долговечность не проверялся.
- Полное удаление строки пользователя: `hw_seq` пропадёт, нужна отдельная таблица верхних отметок или эпоха в ключе. Не реализовано.
- Реальные Telegram/CRM, реальное время (часы симулированные), RLIMIT.
- `figram_client.py` и Go-хост — не мои; сравнение Go с Python делает агент Go-хоста по общим артефактам.
- booking сравнивается с эталоном агрегатно (победитель гонки зависит от тайминга, описано в README).
- Модель домена в checker написана мной по domain.md: ошибку, общую с моей реализацией хоста, она не заметит. Частично это компенсируют эталон «тот же корпус без сбоев» и исходные действия движка.
- Нагрузка измерена на общей перегруженной машине: числа шумные, p99 при 1000 пользователях упирается в fsync SQLite.
- Не утверждаю, что ошибок больше нет. Покрытие: 15 сценариев, 30 красных прогонов, все 25 инвариантов видели красными.
