## 3a. Контракт хоста: подробности находок

### HP-01. Условия вычисляются до исполнения `call` из outbox (HOST §1.3 + §2)

HOST §1.3 велит вычислять условия «по данным той же версии, что и снимок», а §2 — исполнять
действия «отдельным исполнителем» позже. Эффект `call` предыдущего шага (`add_to_cart`, `debit`)
к моменту вычисления условия следующего события того же пользователя может ещё не наступить:
«версия данных, соответствующая снимку» по контракту не включает зафиксированные, но не исполненные
действия. Сам пример контракта (pizza: `cart_not_empty` зависит от `add_to_cart`) подвержен этому.

### HP-03. «Подтверждать после фиксации» + getUpdates + параллельные пользователи теряет обновления

нет. Правка §1.5: описать оба транспорта; для getUpdates — inbox или подтверждение только до

### HP-04. Отсев повторов «вместе со снимком» растёт без ограничения (§1.2)

### HP-05. Порядок и отказы исполнителя outbox не заданы (§2)

§2 требует порядок только «внутри одного ответа» и не говорит, что делать с постоянным отказом.
* h3d: 4 исполнителя без разбиения по пользователю (40 пользователей, `cart → catalog → cart`):
  у 11–12 из 40 потеряно напоминание (два прогона; `start_timer` старого шага исполнен после
  нового или `cancel_timer` после `start_timer` — в планировщике не тот жетон), 39–41
  перестановка сообщений.
  С очередью на пользователя — 0 и 0.
* h3c: постоянный отказ CRM для одного пользователя при строгом порядке — исполнение встало
  у всех (сообщений другим 0 из 15, в очереди 17 действий 6 пользователей). С очередью на
  пользователя и dead letter после 3 попыток — 15 из 15.
* h1c: один общий FIFO (как в host_sim) — медленный вызов одного задерживает всех (и через HP-01
  меняет их ветки).
Правка §2: «действия одного пользователя — строго по порядку фиксации (seq, номер), включая разные

### HP-06. Данные события недоступны условиям и действиям (§1.3, §1.4)

`in_delivery_zone` (адрес в зоне) зависит от текста сообщения, а `save_address` сохраняет его.
Буквальный хост считает условие по сохранённым данным (адреса ещё нет) → `pickup` вместо `pay`.
Если условие читает текст события, но outbox хранит только `{"call": "save_address"}` (так в §1.4),
исполнитель не знает адреса: заказ уходит в CRM с `address = None` (h5). Правка: «вместе с
действиями в той же транзакции сохраняйте данные события, нужные действиям; функции условий
получают событие».

### HP-08. Детерминированные ошибки движка повторяются бесконечно (§5)

### HP-09. `send` не идемпотентен, и совет §2 не закрывает окно (DOC)

## 3b. Производительность: подробности находок

### HP-10. Загрузка документа растёт как N^2.5…N^3: > 10 с уже при ~2000 сообщений (PRODUCT)

Код (`Figram/Compile.lean:52`, `Figram/Chart.lean`, `Figram/Lint.lean`, `Figram/Engine.lean:205`):
* `compile.rows` = для каждого сообщения L × каждого различного события e документа
  (`c.events`) — `compileRow L e` → `cands L e` = `(anc L).flatMap (branchesAt · e)`;
  `anc` поднимается по родителям через `find` (линейный поиск по всем узлам) — O(d·N),
  `branchesAt` фильтрует все стрелки — O(T) на каждого предка. Итого O(L·E·d·(N+T)).
  Если у сообщений свои кнопки/таймеры, E ~ N → O(N³·d).
* `resumes` → `histCands s` = фильтр всех сообщений по `s ∈ anc l` — O(R·L·d·N).
* `Doc.check` → `lint` → `c.compile.wf` компилирует автомат **первый раз**, `Engine.load`
  компилирует **второй раз**; `wf` проверяет `n ∈ m.states` списком для каждого варианта
  (O(строк·B·N)); `lint` — `ids.filter` и `anc` на каждый узел (O(N²·d)).

Замеры (`LOGS/40*/41*/44–49*-series-*.jsonl`; «CPU» — процессорное время всех потоков до `hello`):
* общие события (≈5 на сообщение): 1000 → 1.5 с CPU, 2000 → 7.8 с, **3000 → 22.1 с CPU**
  (21.6–29.7 с wall в двух прогонах; показатель роста ≈2.5);
* `figram random`: 300 → 2.1 с, **1000 → 65 с CPU** (67–90 с wall; показатель ≈2.8);
* уникальные кнопки + 10 % таймеров: 300 → 4.5 с, 600 → 38 с, **1000 → 196 с CPU (221 с wall)**,
  **2000 — не загрузился за 300 с** (`LOGS/49-unique2000-load.log`; показатель ≈3.0–3.3);
* глубина вложенности при 300 сообщениях: d=32 → 7.8 с, **d=64 → 39 с**;
* разделы с «вернуться» при 1000 сообщений: R=100 → **16.7 с** (≈0.15 с на раздел);
* глобальные команды при 1000 сообщений: G=100 → 16 с, G=300 → 46 с CPU, **G=1000 → 189 с CPU**.
* Разложение (`load_breakdown.sh`, `LOGS/62*`, `LOGS/63*`): разбор JSON + decode (`figram fmt`) —
  0.04–0.07 с; `figram check` — 10.9 с (3000 сообщений) и 33.3 с (random 1000); загрузка движка —
  21.3 и 62.8 с. То есть разбор ничтожен, `check` (с первой компиляцией внутри `lint`) — ровно
  половина, вторая половина — повторная компиляция и `wf`.
Граница «> 10 с»: ~2100 сообщений с общими событиями, ~450 для `figram random`, ~350 при
уникальных кнопках, глубина ~40 при 300 сообщениях, ~60 разделов с «вернуться» или ~60
глобальных команд на 1000 сообщений. Пересекается с замерами «широких» документов агента
core-compiler (`agents/core-compiler/LOGS/wide-docs.*`): там форма без стрелок, здесь —
реалистичные формы и шаг.
Последствия: каждый процесс движка (пул клиента Python, каждый перезапуск после сбоя по HOST §5,
каждое обновление документа по §6) тратит это время целиком; см. HP-11.
README «1000 сообщений — 1 с» верно только для одного раздела с одной стрелкой на сообщение
(серия `readme`: 1001 сообщение — 1.2 с).
Исправление: индексы вместо списков при компиляции (карта узел → родитель/предки, карта
(узел, событие) → стрелки, события только у предков L, а не все события документа), одна
компиляция на загрузку (передать результат из `lint` или не вызывать `compile.wf` в `check`
движка), `wf` по множеству состояний. Регрессионный тест: `run_series.py --series states`
с порогом времени загрузки (например, 3000 сообщений < 2 с).

### HP-11. Клиент Python с таймаутом по умолчанию не может стартовать движок на большом документе (INTEGRATION, если скопировать)

уникальными кнопками). То же при каждой замене процесса после сбоя (HOST §5) и обновлении

### HP-12. Шаг — линейный поиск по строкам автомата и сообщениям; > 10 мс при ~10^6 строк (PRODUCT)

числа событий у него и разделов выше — глобальная команда на корне добавляет строку **каждому**
сообщению. CPU на шаг (p50 / p99): 5k строк — 71 / 345 мкс, 35k — 269 / 899 мкс, 105k — 752 мкс /
2.2 мс, 305k — 3.5 / 8.9 мс, **1 005 000 строк (1000 сообщений × 1000 глобальных команд) —
12.6 / 24.5 мс** (`LOGS/48-series-global_big.log`; RSS 146 МБ, загрузка 189 с CPU). Порог 10 мс:
p99 — около 350k строк, p50 — около 800k строк (≈ 12 нс на строку). Снимок с 100 запомненными
разделами (1.7 КБ) — 248 мкс против 36 мкс без них; `figram random 1000` (снимок 3.3 КБ) —
437–531 мкс p50.
Исправление: при загрузке построить `HashMap (узел, событие) → строка`, `HashSet` состояний,

## 4. Инварианты, которые стоит требовать от хоста, и правки HOST.md

| # | инвариант | чем нарушается в буквальном HOST.md | правка |
|---|---|---|---|
| I1 | **Линеаризуемость на пользователя.** Зафиксированные шаги пользователя = последовательное применение `step` к принятым событиям в одном порядке; каждое принятое событие применено ровно один раз | HP-03 (накопительный ack getUpdates теряет событие), HP-08 (детерминированная ошибка — событие не применяется никогда) | §1.5: inbox или ack до наименьшего незавершённого; §5: разделить транзиентные сбои и `error` |
| I2 | **Read-your-writes для условий.** Условия события eₖ пользователя u вычисляются на данных, где применены эффекты всех `call` шагов e₁…eₖ₋₁ этого u и не применены эффекты eₖ; условия могут читать данные eₖ | HP-01 (асинхронный outbox), HP-06 (данные события) | §1.3: барьер на пользователя или локальные `call` в транзакции снимка; функция условий получает событие |
| I3 | **Идентичность действия не переиспользуется.** Ключ действия однозначно определяет логическое действие «ответ на обновление X, действие a» и не повторяется после потери/удаления снимка, `start`, `restart`, отката базы, отката движка | ET-01/ET-03 (`start`/старый снимок), HP-02 (откат базы → дубль; подавление `send`) | §1.4: `пользователь:update_id:действие:вхождение`, либо `пользователь:эпоха:seq:номер`; верхняя отметка `seq` — вне откатываемой базы (998a539 частично) |
| I4 | **FIFO на пользователя, независимость пользователей.** Действия u исполняются в порядке (seq, номер) через все ответы; отказ действия u задерживает только u | HP-05 (h3d, h3c, h1c) | §2: очередь на пользователя; dead letter + событие; срок таймера от фиксации |
| I5 | **Эффекты:** вызовы с ключом — effectively-once; `send` — at-least-once с явным окном дубля | HP-09 | §2: честная формулировка про `send` |
| I6 | **Ограниченное состояние отсева.** Окно ≥ горизонта повторной доставки (Telegram — 24 ч; планировщик — до срабатывания таймера) | HP-04 | §1.2: отдельная таблица с TTL; таймерные `update_id` хранить до срабатывания/отмены |
| I7 | **Доступность данных события действиям.** Данные события, нужные `call`, фиксируются в той же транзакции, что и действие | HP-06 | §1.4 |
| I8 | **Обратная связь об отказе.** Постоянный отказ `call` даёт определённый исход (dead letter, оповещение, событие `call_failed:<имя>` в автомат), а не «снимок `done`, заказа нет» | HP-05 (h3c) | §2 (+ возможно, событие в FORMAT) |
| I9 | **Готовность движка.** Хост ждёт загрузки документа (hello) дольше времени загрузки; таймаут запроса не включает загрузку | HP-11 | README/HOST §5 + клиент: отдельный таймаут старта |

Предлагаемые формулировки (дословно для HOST.md):

* §1.3 — «Условия вычисляются по данным, где уже применены все действия `call`, зафиксированные
  предыдущими шагами этого пользователя (и только ими). Если outbox исполняется асинхронно, перед
  шагом события пользователя дождитесь исполнения его незавершённых действий, либо исполняйте
  вызовы, меняющие данные условий, в той же транзакции, что и снимок. Функции условий доступны
  данные самого события (текст, payload).»
* §1.4 — «…каждое с ключом `пользователь:update_id:действие:n` (n — номер вхождения действия
  в ответе) и с данными события, нужными действию. Ключ `пользователь:seq:номер` уникален только
  пока история снимков пользователя не ветвится (см. §4, §6, восстановление базы).»
* §1.5 — «Webhook: подтверждение — ответ 2xx после фиксации. getUpdates: подтверждение
  накопительное (offset подтверждает все меньшие update_id) — сначала запишите полученные
  обновления во входящую очередь в базе, затем запрашивайте следующий offset; обрабатывайте из
  очереди.»
* §1.2 — «Обработанные update_id храните в отдельной таблице (пользователь, update_id) с TTL не
  меньше 24 ч; для таймеров — до срабатывания или отмены.»
* §2 — «Действия одного пользователя исполняются строго в порядке фиксации (seq, номер), включая
  действия разных ответов; разных пользователей — независимо. Постоянный отказ после N попыток —
  в dead letter с оповещением; остальные пользователи не ждут. `send` — at-least-once.»
* §5 — «Ответ `error` движка детерминирован: повтор его не исправит. Такое событие — в dead
  letter с оповещением, очередь пользователя продолжается.»
