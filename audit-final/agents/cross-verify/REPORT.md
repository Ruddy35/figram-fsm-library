### CV-C1 — условия вычисляются до того, как outbox исполнил call того же пользователя
- **Модуль и класс:** HOST.md §1.3 + §2; PRODUCT (контракт хоста).
- **Вердикт:** CONFIRMED-INDEPENDENTLY.
- **Путь в продакшене:** обычный путь. Хост сделан строго по HOST.md: блокировка на пользователя, отсев повторов, step/need, атомарная фиксация снимка+outbox, подтверждение после фиксации, отдельный исполнитель. Данные для условий читаются в момент шага.
- **Триггер:** задержка исполнителя (CRM или очередь) больше интервала между двумя обновлениями пользователя.
- **Результат:**
  - pizza: btn:add, через 50 мс btn:checkout → cart_not_empty=false (cart=0), at='catalog', ожидалось 'address'. Контроль (исполнитель 0 мс) → address.
  - Бот с балансом (собственный документ): два btn:buy → оба раза has_balance=true, баланс −100, выдано 2 товара. Контроль: no_money, 1 товар.
- **Команда:** `python3 xverify/c1_guard_before_outbox.py <ENGINE> examples/pizza.bot.json <SCR>`, exit 0 на обоих движках.
- **Логи:** LOGS/c1-guard-before-outbox-{bin,fresh}.log.
- **Серьёзность:** Risk 7, P1 — согласен.
  - Аргументы за снижение: в pizza это неверная, но обратимая ветка; двойная выдача требует, чтобы списание не проверяло инвариант на стороне платёжного сервиса.
  - Почему всё же P1: это канонический паттерн самого примера (call add_to_cart → условие cart_not_empty). Эталонный host_sim.py его не ловит, потому что его условия всегда True.
- **Предлагаемое исправление:** в HOST.md — барьер на пользователя (перед step дождаться исполнения всех записей outbox этого пользователя) либо исполнять внутри транзакции call, которые меняют данные условий. host_sim должен вычислять условия по реальным данным.
- **Регрессионный тест:** c1 с барьером должен дать address и один товар.

### CV-C2 — накопительное подтверждение getUpdates теряет обновление
- **Модуль и класс:** HOST.md §1.1 + §1.5; PRODUCT/DOC.
- **Вердикт:** CONFIRMED в модели. Семантика Telegram подтверждена офлайн: docstring python-telegram-bot 21.6 (wheel из зеркала PyPI, sha256 в LOGS/c2-telegram-semantics-offline.txt) — «An update is considered confirmed as soon as getUpdates is called with an offset higher than its update_id». Живой Bot API не проверял: сети нет.
- **Путь в продакшене:** getUpdates-хост с параллельной обработкой пользователей (§1.1) и подтверждением после фиксации (§1.5) через offset = update_id + 1.
- **Триггер:** падение процесса (kill -9 / OOM / деплой), когда B уже подтверждено, а A ещё не зафиксировано.
- **Результат:**
  - naive: offset=1003; после перезапуска getUpdates вернул []; A остался в 'pay', create_order нет — заплатил, а заказа нет.
  - watermark (контроль): после перезапуска пришли [1001, 1002]; A в 'done'; один create_order; 1002 отсеян как повтор.
- **Команда:** `python3 xverify/c2_cumulative_ack.py <ENGINE> examples/pizza.bot.json`, exit 0 на обоих движках.
- **Логи:** LOGS/c2-cumulative-ack-{bin,fresh}.log.
- **Серьёзность:** Risk 5, моя оценка P2 (заявлено P1). Нужны getUpdates, параллельность, наивный offset и падение в узком окне. Webhook-хосты (подтверждение каждого обновления ответом 2xx) не затронуты. P1 оправдан только для ботов на getUpdates с платежами.
- **Дополнительно:** Updater из python-telegram-bot 21.6 ставит `_last_update_id = updates[-1].update_id + 1` сразу после постановки пакета в очередь, до обработки (telegram/ext/_updater.py:407). На нём §1.5 в режиме polling невыполним вообще.
- **Предлагаемое исправление:** в HOST.md — для getUpdates offset двигается только до наименьшего незафиксированного update_id; для webhook отвечать 200 после фиксации.

### CV-C4 — один медленный запрос валит всех на общем процессе
- **Модуль и класс:** figram_client.py `_Process.call/_fail`; INTEGRATION. Корень медленности — PRODUCT: Figram/FormatIO.lean:157, `acc.any` даёт O(K²) на ключ объекта.
- **Вердикт:** CONFIRMED-INDEPENDENTLY (механизм).
- **Триггер:** снимок с K=60000 записей resume; прямой запрос в движок — 14.7 с (bin) / 15.3 с (fresh).
- **Масштаб (LOGS/c4-resume-scaling-bin.log):** K=10k → 0.35 с, 20k → 1.5 с, 40k → 6.5 с. Время почти целиком уходит на разбор JSON (`figram json`).
- **Результат:** 3 попытки «ядовитого» запроса по 10 с; у 32 обычных пользователей 96 отказов «нет ответа за 10.0 с» — они стояли в очереди за ним, и процесс был убит. Контроль без «яда»: 0 отказов.
- **Команда:** `python3 xverify/c4_c5_shared_process.py <ENGINE> examples/pizza.bot.json c4 60000 10 2`, exit 0 на обоих движках.
- **Логи:** LOGS/c4-slow-request-{bin,fresh}.log, LOGS/c5-control-*.log.
- **Серьёзность:** Risk 3, моя оценка P3 сама по себе (заявлено P2). Движок такие снимки не порождает: resume копит только разделы документа, плюс старые, которые никогда не удаляются. Значит, нужен испорченный или подделанный снимок в БД. P2 — только вместе с C3/C6: каждое убийство процесса ведёт к перезагрузке дольше таймаута.
- **Предлагаемое исправление:**
  - клиент: таймаут проваливает только свой запрос (id помечается брошенным, поздний ответ отбрасывается), процесс не убивается;
  - движок: проверка дублей ключей через множество — O(K log K);
  - хост: ограничение размера снимка.

### CV-C5 — неразбираемый запрос → id:null → клиент убивает общий процесс

### CV-C7 — топология исполнителей outbox
- **Модуль и класс:** HOST.md §2/§3; PRODUCT (контракт хоста).
- **Вердикт:** CONFIRMED в модели. Действия — из реальных ответов движка.
- **Результат:**

  - 1a: cancel исполняется медленнее start → у планировщика нет idle → напоминание потеряно.
  - 1b: 4 исполнителя на общем FIFO → у 17 из 40 пользователей таймер отсутствует или с устаревшим жетоном. Деление по пользователю → 0 из 40.
  - 2: строгий глобальный FIFO и вечный отказ CRM на create_order одного пользователя → за 2 с выполнено 0 из 10 действий других пользователей. FIFO на пользователя → 10 из 10.
- **Команда:** `python3 xverify/c7_outbox_executors.py <ENGINE> examples/features.bot.json examples/pizza.bot.json`, exit 0 на обоих движках.
- **Логи:** LOGS/c7-outbox-executors-{bin,fresh}.log.
- **Серьёзность:** Risk 4, P2 — согласен. HOST.md говорит об одном исполнителе «по порядку», но не говорит, как масштабировать и что делать с вечными отказами.
- **Дополнительно:** фраза §3 «отмена — оптимизация, а не условие корректности» неверна при переупорядочивании: cancel стирает более новый start. У cancel_timer нет жетона.
- **Предлагаемое исправление:** outbox делится по пользователю; dead-letter для вечных отказов; cancel с ключом seq=n удаляет таймер только если хранимый жетон меньше n (или добавить жетон в cancel_timer).
