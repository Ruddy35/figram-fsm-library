**Проверяемый контракт** (docstring клиента, HOST.md §5, REVIEW.md N01, V3-01, V3-06, V4-02…V4-05, AUDIT.md):
- C1. Любое нарушение протокола — невалидный JSON, чужой или нецелый id, ответ неверной формы, обрыв вывода, падение, таймаут — помечает процесс неисправным, **будит все** ожидающие вызовы ошибкой и убивает процесс. Следующий запрос уходит в новый процесс.
- C2. Вызов ждёт не дольше `timeout` от начала, включая очередь на запись; вызывающий поток не блокируется на вводе-выводе.

- C4. `step` не возвращает `need`; ошибки функции условий → `EngineError` (V4-02).
- C5. Аварийный процесс собирается сразу, без зомби; `close()` ограничен по времени (V3-01, V4-04).
- C6. «Пользователь всегда попадает в один процесс, поэтому его события обрабатываются строго по порядку отправки» (docstring модуля).
- C7. Хост повторяет запросы, завершённые `EngineError` (HOST.md §5). Значит, все отказы клиента обязаны быть `EngineError`.

### PC-01 — одиночный суррогат: чужое исключение и утечка `_pending`

- **Reachable path.** Хост строит событие или поле снимка из текста Telegram и вызывает `Engine.step`. Нарезка текста по UTF-16-смещениям entities — известный источник одиночных суррогатов в Python-ботах.
- **Trigger.** Любая `str` с одиночным суррогатом в `event`, `snapshot` или `guards`.
- **Impact.** `json.dumps(ensure_ascii=False)` проходит, а `line.encode()` бросает `UnicodeEncodeError` — уже после регистрации вызова в `_pending`:
  1. исключение не `EngineError`, поэтому путь «повторить» из HOST.md §5 не срабатывает, и обработчик падает;
  2. запись в `_pending` не удаляется никогда: 1000 вызовов дают 1000 записей, и память растёт, пока жив процесс.

  На провод такая строка не попадает.
- **Likelihood.** Низкая–средняя. Risk 4, P2, CONFIRMED.
- **Repro.** `python3 r01_surrogate_pending_leak.py`
  - expected: 1000 × EngineError, ожидающих 0;
  - actual: `{'UnicodeEncodeError': 1000}`, ожидающих 1000;
  - exit 1; лог `LOGS/prebuilt_r01_surrogate_pending_leak.log`.
- **Fix.** Сериализация и кодирование выполняются до регистрации вызова; `UnicodeEncodeError` — подкласс `ValueError`, поэтому становится `EngineError`.
- **Regression.** R5.
- **Fix commit.** 51c31ce.
- **Retest.** `CLIENT_DIR=/home/user/figram-audit-worktrees/python-client/ffi/python-example python3 r01_surrogate_pending_leak.py` → `{'EngineError': 1000}`, ожидающих 0, exit 0 (`LOGS/bin_retest_r01.log`).

### PC-10 (проверка гипотезы FS-4) — ответ id:null убивает общий процесс

- **Module.** `_read_loop`: ответ без целого id → `_fail`. Парная сторона — `Engine.handle`: на любую ошибку разбора текста движок отвечает `{"id":null,"error":…}`. Это уже подтвердили на настоящем движке агенты formats и engine-timers; они же подтвердили FIFO-порядок ответов. Здесь разобрано только поведение клиента.
- **Что клиент реально отправляет** (r10, `LOGS/bin_probe_engine_replies.log`):
  - ключи `1` и `"1"` → `{"1":"menu","1":"menu"}`;
  - ключи `True` и `"true"` → `{"true":1,"true":2}`;
  - вложенность 300 проходит `json.dumps`;
  - одиночный суррогат на провод **не попадает** (это PC-01).
- **Граница глубины** совпадает с движком точно: 256 контейнеров → обычная ошибка с id, 257 → id:null (`LOGS/bin_depth_boundary_baseline-client.log`).
- **Reachable path.** Снимок из хранилища хоста с нестроковыми ключами (msgpack, ORM, ручная сборка) или испорченный/глубоко вложенный → `Engine.step`.
- **Impact.** Клиент считает id:null нарушением протокола: SIGKILL общему процессу, все ожидающие запросы других пользователей получают `EngineError`.
  - 20 плохих запросов → 20 перезапусков и 88 ошибок у 7 соседей;
  - повтор плохого запроса хостом (HOST.md §5) перезапускает процесс каждый раз;
  - контроль (обычная ошибка с id): у соседей 0 ошибок, процесс один.
- **Likelihood.** Низкая: нужен аномальный снимок. Risk 4, P2, CONFIRMED (настоящий движок).
- **Repro.** `python3 r10_id_null_poison.py`, exit 1 (`LOGS/bin_r10_id_null_poison.log`).
- **Fix (клиент).** `_check_wire` до регистрации вызова: ключи — только `str`, вложенность ≤ 256 (= `FormatIO.maxDepth`); `RecursionError` тоже становится `EngineError`.
  - Изменение поведения: снимок с нестроковыми ключами теперь отвергается даже без дубля.
- **Regression.** R8. **Fix commit.** 51c31ce.
- **Retest.** У соседей 0 ошибок, процесс один во всех 5 случаях (`LOGS/bin_retest_r10.log`; надпись «FS-4 не подтверждена» на исправленном клиенте означает, что дефекта нет). Граница: 257 → «вложенность больше 256», процесс тот же (`LOGS/bin_depth_boundary_python-example.log`).
- **Остаточный риск.** Любая другая причина id:null по-прежнему роняет соседей. Рекомендация PRODUCT/FORMAT — одно из двух:
  - движок отвечает с id, если строка начинается с `{"id":<целое>`;
  - FORMAT.md закрепляет FIFO-порядок ответов, и клиент сопоставляет id:null с самым старым неотвеченным запросом.

### PC-06 — «ядовитый» медленный запрос плюс повтор — отказ для соседей

- **Module.** `_Process.call`: таймаут любого вызова → `_fail` всего процесса. Плюс HOST.md §5: повторять без ограничения.
- **Reachable path.** Запрос, который движок не успевает выполнить за `timeout` (аномально большой снимок, голодание CPU). Хост повторяет его, Telegram заново доставляет неподтверждённое обновление.
- **Impact.** 7 обычных пользователей того же процесса:
  - без яда — 4622 шага, все успешные;
  - с ядом (resume из 30 000 записей, timeout 2 с) — 28 шагов, 0 успешных, 4 перезапуска за 8 с.

  При P процессах страдает примерно 1/P пользователей, пока длятся повторы.
- **Likelihood.** Низкая для нормальных снимков, но само усиление «один запрос → все соседи» заложено в дизайне. Risk 4, P2, CONFIRMED.
- **Repro.** `python3 r06_poison_request.py 30000 8`, exit 1 (`LOGS/prebuilt_r06_poison.log`). Время движка — `LOGS/bin_big_snap_timing.log`.
- **Proposed fix.** Не исправлено: нужно решение владельца.
  - HOST.md: ограничить число повторов; запрос, упавший N раз, — в dead-letter.
  - Клиент: ограничить размер запроса; не убивать процесс, который отвечает другим (проверка живости через `hello`).

- **Impact.** Из `start()`/`step()` летит `FileNotFoundError` (3 из 3) — в обход контракта повтора HOST.md §5. Конструктор `Engine()` по-прежнему бросает OSError: это ошибка конфигурации при старте, её оставил как есть.
- Risk 2, P2, CONFIRMED.
- **Repro.** `python3 r03_missing_binary.py`, exit 1 (`LOGS/prebuilt_r03_missing_binary.log`).
- **Fix.** `OSError` при запуске замены оборачивается в `EngineError`. **Regression.** R7. **Fix commit.** 51c31ce.
- **Retest.** `{'EngineError': 3}`, exit 0 (`LOGS/bin_retest_r03.log`).

### PC-05 — нет паузы между перезапусками, причина отказа теряется

- **Trigger.** Документ не загружается (движок сразу выходит с кодом 1), хост повторяет.
- **Impact.**
  - 8 повторяющих потоков → 275 запусков движка за 5 с (55/с), 2.19 с CPU у потомков.
  - Хост видит «движок закрыл вывод» или «BrokenPipeError», но не «ошибка документа: нужно поле «figram»» — движок печатает это в stderr, а stderr уходит в DEVNULL (проверено).
  - `Engine()` с невалидным документом создаётся без ошибки.
  - Форк-бомбы нет: в r04 baddoc (500 циклов) fd, потоки и зомби стабильны.
- Risk 3, P3, CONFIRMED.
- **Repro.** `python3 r05_spawn_storm.py 5 8`, exit 0 — это измерение (`LOGS/prebuilt_r05_spawn_storm.log`).
- **Proposed fix.** Не исправлено.
  - `hello` при запуске процесса: проверка документа и версии протокола.
  - Хвост stderr — в текст `EngineError`.
  - Экспоненциальная пауза между перезапусками слота.

### PC-08 — неверное утверждение о порядке событий

- **Суть.** Движок не хранит состояния: результат зависит только от переданного снимка. Привязка пользователя к одному процессу порядка не обеспечивает.
  - (a) Два события без блокировки хоста: итог `seq 2` вместо `3`, одно событие потеряно.
  - (b) Процесс упал, когда в очереди стояли e1 и e2: оба получают `EngineError`, порядок повторов решает планировщик потоков. e2 зафиксирован раньше e1 в 12 из 40 прогонов.
- **Кого задевает.** HOST.md §1.1 требует блокировку на пользователя, поэтому корректный хост не страдает. Риск — для интегратора, который поверил docstring.
- Risk 3, P3, CONFIRMED.
- **Repro.** `python3 r08_ordering.py 40`, exit 1 (`LOGS/prebuilt_r08_ordering.log`).
- **Предлагаемый текст docstring:** «Привязка пользователя к процессу нужна только для распределения нагрузки; порядок событий и целостность снимка обеспечивает хост блокировкой на пользователя (HOST.md §1.1). При сбое процесса все его запросы завершаются ошибкой, и повторы могут прийти в любом порядке.» Docstring не менял: документ без теста.

### PC-12 — SIGKILL по уже собранному pid

- **Суть.** На один сбой `_fail` вызывается до трёх раз (читатель видит EOF, писатель — EPIPE, вызывающий — таймаут), и каждый раз выполняется `os.killpg(pid)`. Фоновый `wait()` к этому моменту может уже собрать процесс.
- То же при каждом штатном `close()`: `close` собирает процесс, затем читатель видит EOF → `_fail` → `killpg`.
- **Счёт на baseline:**
  - 500 сбоев — 117 из 1663 вызовов `killpg` ушли по свободному pid;
  - 300 сбоев — 838 вызовов на 594 pid, 57 по собранному.

  `kernel.pid_max=32768`. Если pid за это окно займёт лидер другой группы (процессы пула сами лидеры групп: `start_new_session=True`), SIGKILL получит чужая группа.
- **Likelihood.** Очень низкая: нужен оборот pid за миллисекунды. Risk 2, P3; шаблон CONFIRMED, промах по чужой группе — HYPOTHESIS.
- **Repro.** `python3 r12_killpg_after_reap.py 500`, exit 1 (`LOGS/bin_r12_killpg_after_reap.log`).
- **Fix.** Процесс убивается только при первом `_fail`, до запуска `wait`; `close()` помечает процесс заранее и убивает только несобранный.
- **Regression.** R9. **Fix commit.** 51c31ce.
- **Retest.** 0 по собранному pid; ровно один `killpg` на pid — 596 вызовов на 596 pid (`LOGS/bin_retest_r12.log`, `LOGS/bin_r12_pids_python-example.log`).

- Возможная связь с V5-02 в REVIEW.md («первопричина не установлена») — HYPOTHESIS.
- Risk 2, P3, CONFIRMED. **Fix commit.** 2550540.

### PC-07 — длина строки ответа не ограничена

- **Суть.** Читатель — `for raw in stdout` без предела длины. Двойник: `exec cat /dev/zero`.
- **Пик RSS клиента:** 64 МБ при timeout 0.25 с, 138 МБ при 0.5 с, 293 МБ при 1.0 с, 694 МБ при 4.0 с. При timeout по умолчанию 10 с это порядка 1.7 ГБ на нагруженной машине, а на свободной — больше. Настоящий движок так себя не ведёт: размер ответа порядка размера запроса.
- Risk 2, P3, CONFIRMED (двойник).
- **Repro.** `prlimit --as=6000000000 -- python3 r07_endless_line.py 0.25 0.5 1.0` (`LOGS/prebuilt_r07_endless_line*.log`, exit 0 — измерение).
- **Proposed fix.** `readline(limit)` с настраиваемым пределом; превышение — нарушение протокола. Не исправлено.

### PC-15 — закрытие пула занимает N × timeout

- `Engine.close` закрывает процессы по очереди, и каждый ждёт до `timeout`.
- Двойник, который не читает вход и не выходит по EOF: 4 процесса, timeout 1 с → 4.01 с. При 8 процессах и timeout 10 с остановка займёт до 80 с.
- **Repro.** `python3 r14_close_latency.py 4 1.0` (`LOGS/bin_r14_close_latency.log`).
- P3, Risk 1. **Proposed.** Закрывать параллельно с общим сроком.

### PC-16 — у `Engine.step` нет общего срока

- Два вызова движка (need → guards) с отдельными сроками плюс время guards. guards на 1.5 с при timeout 1 с → step занимает 1.5 с без ошибки (`LOGS/bin_r11_guards_close.log`, случай c).
- Код так и задуман, но обещание «не дольше timeout» относится к одному вызову, а не к step.

### PC-18 — принимается ответ с UTF-8-кодированным суррогатом

- `json.loads(bytes)` декодирует с `surrogatepass`: ответ `{"at":"\xed\xa0\x80"}` принят (r09).
- Хост получает снимок с `'\ud800'`, и на следующем запросе это даёт PC-01; после исправления — чистую `EngineError`.
- Настоящий движок так не ответит: строки Lean — скалярные значения Unicode.
- P3, Risk 1. **Proposed.** Строгий `raw.decode("utf-8")` перед `json.loads`.
