## 1. Область и контракт

* **C-ABI.** Функции: `figram_init`, `figram_check_json`, `figram_fmt_json`, `figram_load_doc`, `figram_request_json`, `figram_unload`, `figram_free`. Экспорт Lean (`@[export]`): `figram_check`, `figram_fmt`, `figram_load`, `figram_request`.
* **Владение.** У экспортных функций все параметры владеющие (`LCNF/InferBorrow.lean`: exported → `borrow := false`). Сгенерированный `Api.c` передаёт `m` и `line` в `Engine.handle` без `lean_dec`. C-прослойка этому соответствует: свежие строки из `lean_mk_string`, `lean_inc(m)` перед вызовом. В `figram_load_doc` поле `m` удерживается своим `lean_inc`, затем `lean_dec(o)`, затем `lean_mark_mt(m)` — это корректно: `m` не может освободиться. MT-объекты никогда не `lean_is_exclusive`, поэтому разделяемый автомат не изменяется на месте.
* **Неявный контракт, нигде не записанный** (заголовка нет):
  - init вызывается раньше всего остального;
  - аргументы не NULL;
  - строки NUL-терминированы, а значит не могут содержать NUL;
  - результат освобождается через `figram_free`;
  - `figram_unload` нельзя вызывать параллельно с запросами к тому же дескриптору и нельзя использовать дескриптор после неё.
* **Go `Bot`** — INTEGRATION (код, который скопируют). `main.go`/`race_test.go` — EXAMPLE/TEST.

## 3. Находки

Общие поля для всех находок: baseline `d69bbaf`; исправления — в ветке `audit/ffi-go`.

### FFI-01 — одновременный `figram_init` роняет процесс
* PRODUCT (+INTEGRATION: в Go нет `sync.Once`). Риск 4. **P2**. CONFIRMED.
* **Модуль:** `ffi/figram_ffi.c` (`figram_init`). Флаги `ready`, `g_initialized` (рантайм) и `_G_initialized` (модуль) — обычные, неатомарные переменные.
* **Путь:** хост вызывает init из нескольких потоков или горутин (ленивая инициализация в обработчиках, параллельные тесты).
* **Механизм и последствие:** проигравший поток видит, что модуль уже «инициализирован», и сразу работает, пока победитель ещё заполняет замкнутые термы. Итог — SIGSEGV всего хоста.
* **Повтор:** `REPRODUCTIONS/repro_c_baseline.sh`; `ffi/audit/init_race.sh BIN 300`.
* **Ожидалось / получено:** 300 из 300 успешны / 17–29 падений с кодом 139. В Go — 46 из 100 и 32 из 50.
* **Логи:** 11-init-race-before; 11-init-race-tsan (гонка на `figram_ffi.c:46`); 25-go-init-race-before; 60; 61.
* **Исправление (`4998244`):** атомарное состояние once через CAS; одновременные вызовы ждут первый.
* **Регрессионные тесты:** `regress.sh` FFI-01; `TestAuditInitRace`.
* **Перепроверка:** 0 из 300 (42), TSan 0 предупреждений (43), Go 0 из 100 (44).

### FFI-07 — use-after-unload и двойная выгрузка (нарушение контракта, UB)
* PRODUCT. Риск 2. P3. CONFIRMED.
* **Use-after-unload:** после выгрузки и загрузки другого документа запрос по старому дескриптору молча отвечает `"states":0` вместо 11, код 0 (05, 60). ASan этого не видит (06), valgrind показывает 0 ошибок (09-valgrind-uaf).
* **Двойная выгрузка:** недетерминированно — либо тишина, либо SIGSEGV (05, 06, 60).
* **Go:** защищено `RWMutex` и проверкой на nil (шторм-тест), кроме копирования `Bot` по значению.
* **Предложение:** отладочная проверка дескрипторов (таблица поколений); `noCopy` и финализатор в Go. Не исправлено.

### FFI-08 — обрезка по NUL
* PRODUCT (C-ABI) + INTEGRATION. Риск 2. P3. CONFIRMED.
* **Документ:** `Load(doc + "\x00{garbage")` загружается. CLI отвергает те же байты: «лишний текст после JSON» (24, 05, 61).
* **Текст ошибки:** `check_json` на дублирующемся ключе `"a\u0000b"` возвращает сырой NUL, и C и Go видят обрезанное «повторяющийся ключ «a».
* **Запросы Go не затронуты:** `json.Marshal` экранирует NUL.
* **Исправление Go (`a027905`):** `Load` отвергает NUL. Регрессия `TestAuditLoadNUL` → PASS (47).
* **Предложение для C:** варианты функций с длиной; экранировать NUL в тексте ошибок `check`.

### FFI-09 — недокументированные побочные эффекты `figram_init` для хоста
* DOC/PRODUCT. Риск 2. P3. CONFIRMED (05 side_effects, 52-init-fds).
* Что меняется в процессе:
  - SIGPIPE переводится в SIG_IGN для всего процесса;
  - ставится обработчик SIGSEGV/SIGBUS, если его не было (хосты на C);
  - `sigaltstack` вызывающего потока заменяется на буфер 14 528 байт;
  - запускается постоянный поток цикла событий libuv с резервом стека 1 ГиБ;
  - VmSize вырастает с 16 МБ до 2,18 ГБ;
  - открываются 8 дескрипторов с CLOEXEC (epoll, 2× io_uring, 2 pipe, eventfd).
* **В Go наблюдаемых последствий нет:** поведение SIGPIPE не меняется (30), шторм SIGPROF проходит (29).
* **Предложение:** раздел «Встраивание» в README/HOST.

### FFI-13 — нет предела размера запроса, усиление памяти

## 5. Что не смог проверить

* Официальный тулчейн clang/libc++ для `libfigram.a`, C и Go локально, и `ldd` такого Go-бинарника. Есть только лог CI baseline.
* Доказательство отсутствия гонок: TSan здесь неприменим как оракул (FFI-15). Опираюсь на функциональный стресс (16 потоков, pizza, 10 видов запросов).
* linux/arm64, macOS, Windows (более слабая модель памяти).
* Go `-buildmode=c-shared` и plugin: проверена только ошибка компоновки .so.
* Паники рантайма Lean (`lean_panic_fn`) внутри встроенного вызова — область core-compiler.
* Нагрузка дольше 3 минут; фаззинг входов ABI сверх перечисленных случаев (фаззинг JSON — у formats).
* Один раз, без лога, тестовый бинарник Go оказался слинкован со старой `libfigram.a`. Воспроизвести не удалось (46-go-stale-cgo-lib*) — гипотеза снята.
* Замеры производительности шумные: машину делят ~8 агентов, load average 3–4.

Остаточный риск: остальные точки входа не защищены от нарушения контракта (FFI-03, 04, 07). Добавлено только исправление `figram_unload(NULL)`. Нет предела размера запроса (FFI-13). Побочные эффекты и аварийный отказ init не задокументированы (FFI-09, 10).
