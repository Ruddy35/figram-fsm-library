## 1. Область и контракт

Что смотрел: Figram/Engine.lean, Api.lean, EngineMain.lean, Core.lean (шаг), Chart.lean/Compile.lean (порядок вариантов, вход/выход), Mutate.lean, FORMAT.md §7, HOST.md §1 (step/need, ключи `пользователь:seq:номер`), §3 (таймеры), §4 (сброс), §6 (обновление документа).

Контракт: одна строка JSON на запрос, одна строка ответа с тем же `id`. На `need` хост вычисляет условия и повторяет запрос. Снимок хранит хост. Таймер принимается только с текущим жетоном.

Инструменты (свои, не conformance.py), в `/home/user/figram-audit-worktrees/engine-timers/audit/engine_timers/`:
- `ptdriver.py` — драйвер протокола с состоянием и своей эталонной моделью Chart.step (Python, по FORMAT/Chart.lean). Говорит с реальным процессом и после каждого ответа проверяет инварианты I1–I12. Обход: BFS по модели до каждой достижимой тройки «сообщение × событие × выигравший вариант» (включая «ничего не выиграло») и случайные блуждания (частичные guards, устаревшие, чужие и огромные жетоны, повторы, restart, испорченные запросы). Режим `mutants` перебирает все `--mutate` и отделяет эквивалентные мутанты.
- `ptsuite.py` — 54 целевых сценария: PASS/FAIL — проверка документированного поведения, OBS — запись фактического.
- `evil_engine.py` — прокси, который портит ответы; нужен для негативных проверок.
- `check_host_contract.py` — регрессионный тест HOST §4/§6.
- `REPRODUCTIONS/repro.py <случай>` — минимальные воспроизведения; `REPRODUCTIONS/upgrade-docs/` — документы v1/v2.

## 3. Находки

Общие поля для всех: baseline d69bbaf; бинарник bin (CI-verified); лог указан в каждой находке.

**ET-01. HOST §1.4/§4, FORMAT §7, Engine "start". PRODUCT. P1, риск 7, CONFIRMED.**
- Путь: HOST §4 (база) разрешал `start` при утерянном снимке. host_sim.py:105-107 делает `start`, когда снимка нет («удалить мои данные», при этом CRM и outbox хранят ключи).
- Условия: у пользователя уже были действия; дедупликация по ключу, как требует HOST §2.
- Последствие: `start` сбрасывает seq. Тот же путь заказа даёт u:5:0 save_address, u:6:0 create_order, u:6:1 send. CRM возвращает результат первого заказа: второй заказ не создан, адрес не обновлён, а пользователь видит «заказ принят».
- Масштаб: 10/10 ключей совпадают. На 60 случайных парах жизней через движок совпадают 85,3 % ключей действий (outbox с уникальным ключом); 6 из 225 вызовов `call` совпадают тем же вызовом (пространство ключей CRM).
- Вероятность: средняя — сам HOST предлагал этот путь.
- Повтор: `repro.py f1-start-keys` (LOGS/repro-f1-start-keys.log, код 0, VERDICT BUG).
- Ожидалось: ключи не пересекаются. Получено: 10/10 пересечений.
- Исправление (998a539): `start` только для пользователя без действий; `restart` с последним зафиксированным снимком; при утере снимка хост хранит верхнюю отметку seq и вызывает `{"op":"restart","snapshot":{"at":"-","seq":N}}` (движок это поддерживает, S4).
- Тест: check_host_contract.py — FAIL до (код 1), PASS после (код 0, 0 совпадений).
- Предложение для кода: `start` с необязательным seq; перевести host_sim на верхнюю отметку.

**ET-02. Core accepts/fire (exitOf по новой версии) + HOST §6. PRODUCT. P2, риск 5, CONFIRMED.**

**ET-04. Core.requiredGuards / Engine.missing / Trace.guardNames. PRODUCT. P3, риск 3, CONFIRMED.**
