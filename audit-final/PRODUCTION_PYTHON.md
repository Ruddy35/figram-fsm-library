# Production-like хост на Python (процессный движок)

Полный отчёт: `agents/host-python/REPORT.md`. Код: ветка `audit/host-python`, каталог `audit/host-python/`
(коммиты 076831d, 697da15, 3c922e6). Движок: `bin/figram-engine` baseline (CI-verified = официальная свежая сборка).
Общие артефакты сценариев (7 ботов, `domain.md`, 15 корпусов, заморожены SHA-256): `hosts/shared/`.
Выходы: `hosts/out/python/`.

## Архитектура
* Написан с нуля (stdlib + sqlite3); код `host_sim.py` и `go-example` не используется; **собственный транспорт**
  `engine_transport.py` (пул из K процессов на документ, привязка пользователя к процессу по crc32, строгая проверка
  каждого ответа, замена процесса при EOF/EPIPE/таймауте/нарушении протокола). `figram_client.py` не использовался.
* SQLite (WAL, `synchronous=FULL`): `users` (снимок, `version` для оптимистической блокировки, документ, постоянная
  верхняя отметка `hw_seq`), `processed`, `transitions`, `outbox(key UNIQUE)`, `timers`, доменные таблицы; журнал
  внешнего симулятора — отдельная БД.
* Шаг под блокировкой пользователя: снимок → `step` → при `need` правило **G1** (исполнить свои ожидающие `call`),
  **G2** (блокировка дефицитного ресурса до фиксации) → условия из доменной БД → `step` → **одна транзакция**
  (снимок + processed + transitions + outbox + timers) → ack.
* Ключ `пользователь:seq:номер` с иммунитетом к P-01: `start` только для нового пользователя, сброс и ремонт — `restart`
  от `hw_seq`, `outbox.key UNIQUE` как растяжка (коллизия обрывает транзакцию).
* Исполнитель outbox — 4 потока, строки одного пользователя строго по порядку; локальные `call` — в транзакции с
  отметкой «done»; внешние — с ключом; после успешного внешнего эффекта повторяется запись отметки, а не эффект.
* Свой планировщик таймеров на симулированных часах (переживает рестарт), обновление документа v1→v2 с отменой
  осиротевших таймеров (смягчение P-04 на baseline), валидация входящих обновлений (`timer:*`/`token` от Telegram запрещены).
* Стенд: «Telegram»-прогонщик (повтор до ack, повторная доставка неподтверждённого), **настоящий** `kill -9` хоста в 4
  точках с рестартом на той же БД, внешний захват БД, прокси-процесс, портящий ответы движка, SIGKILL движка,
  CRM/TG-симулятор (500/429/timeout/timeout_before/dup/delay/reorder), порча снимков прямо в БД. Независимый оракул
  `checker.py` (своя модель домена + эталон «тот же корпус без сбоев»).

## Результаты
* **15/15 сценариев, все инварианты PASS** (17–22 на сценарий): заказ, бронь с конфликтами, поддержка с history и
  сменой версии посреди разговора, напоминания (устаревший жетон, двойной callback, callback после рестарта), миграция,
  сбои (все 4 точки краха, БД недоступна, обрыв канала движка), нагрузка, протокольные atack-сценарии.
* Внедрено крахов: order 7+7, booking 4+4, support 4, reminders 1+1, migration 2, failures 10+10; 9 ремонтов снимка;
  28 отвергнутых обновлений; повторов движка после сбоев 5–17 на прогон.
* **RED-матрица:** 30 прогонов с реально сломанными вариантами хоста (no-dedup, ack-before-commit, outbox-after-ack,
  const-guards, no-drain, no-resource-lock, seq-keys-start, random-keys, stale-token-lookup, no-validate, memory-timers,
  trust-snapshot, no-ack-retry, no-crash-points…): каждый из 25 инвариантов хотя бы раз красный (`invariants_never_red: []`).
* **Гарантии, которые реально даёт такой хост:** внешний `call` — эффективно один раз (ключ в CRM); локальный `call` —
  ровно один раз (одна транзакция); `send` — **at-least-once**, не exactly-once (дубли объяснены сбоями/таймаутами);
  подтверждённое обновление не теряется; `seq` строго +1; устаревший жетон эффекта не даёт.

## Находки через этот хост
PH-01 = P-01 (новое проявление: `update_id` таймера), PH-02 = P-02, PH-03 (дефицитный ресурс, открыто), PH-04 (send
at-least-once), PH-05 (поддельный `timer:*`, открыто), PH-06 = P-20, PH-07 = P-04, PH-08 = P-05. Собственные дефекты
хоста, найденные его же тестами, исправлены (дубли ключей в JSON, повтор эффекта при ошибке БД, бесконечный NACK).

## Не проверено
Параллельная доставка разных обновлений одного пользователя (webhook `max_connections>1`); хост из нескольких
процессов; сбой ОС/питания (только `kill -9`); полное удаление строки пользователя; реальные Telegram/CRM; booking
сравнивается с эталоном по агрегатам (победитель гонки зависит от тайминга).
