## Изменения поведения и API (`figram_client.py`)
- **Рукопожатие:** каждый процесс сначала получает `{"id":0,"op":"hello"}`; id вызовов по-прежнему с 1. Проверка hello: `protocol == 1` (другая версия — отказ запуска), `states` — целое, `mutant` допускается.
- **Конструктор** ждёт загрузки и при сбое запуска бросает EngineError с причиной. OSError при запуске процесса в конструкторе остался OSError, как было. `wait_ready=False` возвращает прежнее ленивое поведение.
- **Новые параметры:** `start_timeout`, `hang_timeout`, `step_timeout`, `max_line`, `restart_backoff`, `wait_ready`. Сигнатура `Engine(binary, document, processes, timeout)` не менялась.
- **Таймаут** больше не убивает общий процесс.
- **Порядок ответов (FIFO)** теперь обязателен: ответ не по порядку — нарушение протокола. Раньше такие ответы принимались, но настоящий движок всегда отвечает по порядку, а fix-protocol закрепил это в протоколе.
- **stderr** движка: PIPE, вычитывается тем же потоком чтения (через poll, без лишнего потока); раньше уходил в DEVNULL.
- **Пауза перезапуска** (`restart_backoff`): вызовы сразу получают EngineError с текстом «перезапустится через N с; последний сбой: …».
- **`close()`** сразу будит ожидающих с «клиент закрыт» (`retryable=False`).
- **`_check_wire`** оставлен: строку, которую движок не разберёт, клиент отвергает до отправки.
- **Тесты:** sh-двойники сначала отвечают на hello. В R2 и R9 пауза перезапуска отключена (`restart_backoff=(0, 0)`), чтобы сохранить 300 и 200 настоящих замен процесса.
- **HOST.md:** §5 переписан (только часть про клиент), §7 исправлен (было «6 видов сбоев»). FORMAT.md и README не трогал: изменения протокола — зона fix-protocol.

## Риски
- **FIFO.** Клиент полагается на ответы по порядку. Если когда-нибудь движок станет отвечать не по порядку, процессы будут убиваться на первом же таком ответе.
- **Зависший процесс** заменяется не раньше чем через 60 с (по умолчанию); вызовы всё это время получают таймауты. Законный запрос дольше `hang_timeout` приведёт к убийству процесса.
- **Блокировка очереди.** Записанный и брошенный запрос движок всё равно выполнит. Бесконечные повторы медленного запроса держат процесс занятым (r06 на старом парсере). Меры: ограничить повторы (HOST.md §5) и быстрый парсер fix/protocol.
- **Блокирующий конструктор** может удивить код, который создаёт Engine на пути с жёсткими требованиями к задержке; там нужен `wait_ready=False`.
- **Хост, повторяющий без пауз,** во время паузы перезапуска будет крутиться на быстрых ошибках; HOST.md требует пауз между повторами.
- **Конфликты слияния** возможны в HOST.md §5/§7 с правками fix-docs и fix-protocol. С `protocol.py` из fix/protocol клиент совместим: используются только `check_reply` для результата и need и `ProtocolError`.
- **Переносимость:** клиент только для POSIX (`poll`, `waitid`, `killpg`), как и раньше.
