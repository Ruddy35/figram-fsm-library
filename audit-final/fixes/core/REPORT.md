## Риски и чего не сделал

- Шаг остаётся O(число сообщений): около 0,1 мкс на сообщение за проход, проходов несколько; flat_4000 — примерно 0,4–0,5 мс. Чтобы получить O(1), нужны хеш-таблицы внутри `Machine`, а это перестройка ядра и доказательств. В рамки брифа (O(#states + #events)) текущее решение укладывается.
- Компилятор делает O(сообщения × различные события) дешёвых запросов: 2000 уникальных кнопок — 0,3 с, 10 000 по оценке — секунды. Без этого слагаемого нужна сортировка по индексу события с доказательством; не сделал.
- Глобальный экземпляр `decMemStr` (priority high) разрешает `n ∈ (l : List String)` во всём проекте. Смысл тот же, `decide` в ядре работает.
- Предупреждения эвристические: достижимость учитывает префикс вариантов и владение таймером, но не значения условий.
- README «Производительность» обновить не мог — это зона fix-docs; цифры для замены — таблица выше.
- `figram trace` на огромных документах по-прежнему работает по спецификации, то есть медленно; в задачу это не входило.
- Возможные конфликты при слиянии: `Main.lean` (4 строки), `Engine.lean` (`load` и `missing`), FORMAT §3/§7. Модель `need` в `audit/engine_timers/ptdriver.py` и `ptsuite.py` обновил я.
