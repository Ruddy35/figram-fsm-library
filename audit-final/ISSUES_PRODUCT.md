# Дефекты продукта (PRODUCT) — сводный реестр

Только находки, достижимые в работающем продукте: ядро и компилятор Lean, формат и текстовый слой JSON,
протокол движка, бинарники `figram`/`figram-engine`, встраиваемый C-ABI (`figram_ffi.c` + `Api.lean`) и
контракты FORMAT.md / HOST.md. Интеграции (клиент Python, Go-обёртка), примеры и тесты — отдельно
(ISSUES_INTEGRATION.md, ISSUES_TESTS.md).

Дедупликация — по первопричине; в «источниках» перечислены все агенты, которые нашли или **независимо**
подтвердили находку. Базовая ревизия для всех — `d69bbaf`. Пути относительно `audit-final/`:
`agents/<агент>/REPORT.md` — полное описание, `agents/<агент>/LOGS/…` — журналы (команда, код, вывод),
`agents/<агент>/REPRODUCTIONS/…` — воспроизведения. Скрипты тестов, на которые ссылаются агенты, лежат в
ветках `audit/<агент>` (`PATCHES/audit-branches.bundle`). Коммиты исправлений — в ветке `audit/integration`.

Уверенность: CONFIRMED — воспроизведено на настоящем движке (bin, CI-verified, и/или свежая сборка);
«×N» — число независимых воспроизведений. LIKELY — механизм подтверждён в модели, внешняя часть (Telegram) — по
документации.

## P1

### P-01. Ключи идемпотентности повторяются после `start` (потеря заказа)
* **Источники:** ET-01 (engine-timers), PH-01 (host-python), HP-02 h2b (host-perf), независимое
  воспроизведение оркестратора, подтверждение через Go-хост (host-go).
* **Модуль / класс:** HOST.md §1.4 (ключ `пользователь:seq:номер`), §3 (`update_id` таймера
  `timer:<имя>:<жетон>`), §4 (разрешал `start` при утерянном снимке); `Engine` `start` начинает `seq` с 0. PRODUCT (контракт).
* **Путь в продакшене:** «удалить мои данные», утерянный снимок, ручной сброс пользователя поддержкой —
  ровно так, как предлагали HOST §4 и `host_sim.py` (`start`, если снимка нет).
* **Последствие:** все ключи второй «жизни» совпадают с первой; CRM, дедуплицирующая по ключу (как требует
  HOST §2), возвращает результат первого заказа — **второй заказ не создаётся**, а пользователь видит
  «заказ принят». `update_id` таймеров тоже совпадает: срабатывание прошлой жизни принимается досрочно, а
  настоящее отбрасывается как обработанное (PH-01). При дедупликации `send` по ключу бот молчит весь второй заказ (h2b).
* **Вероятность:** средняя — путь описан в самом контракте.
* **Повтор:** `python3 -I REPRODUCTIONS/orchestrator/repro_et01.py bin/figram-engine examples/pizza.bot.json`
  — код **1** = дефект (14 из 14 ключей совпали, `create_order` исполнен 1 раз вместо 2):
  `LOGS/orchestrator/20-orch-repro-et01.log`. Также `agents/engine-timers/REPRODUCTIONS/repro.py f1-start-keys`
  (10/10, 85 % ключей на 60 случайных парах), `agents/host-python/REPRODUCTIONS/run_repro.sh et01_reset_order.jsonl seq-keys-start`.
* **Исправление:** HOST/FORMAT (engine-timers 998a539 → integration **7730517**): `start` — только для пользователя
  без истории; сброс — `restart` с последним зафиксированным снимком или заглушкой `{"at":"-","seq":N}` от
  постоянной верхней отметки `seq` хоста. Оба production-like хоста реализуют это (`hw_seq`) и иммунны (RED-вариант
  `seq-keys-start` краснеет, исправный — зелёный). **Код движка не менялся**; предложение: `start` с необязательным
  `seq` или эпоха пользователя в ключе.
* **Регрессионный тест:** `check_host_contract.py` (engine-timers): baseline-документация — rc 1, после — rc 0
  (`agents/engine-timers/LOGS/host-contract-{BEFORE,AFTER}.log`; на integration — `agents/integration/LOGS/60-*`).

### P-02. Условия считаются раньше, чем исполнены `call` прошлого шага
* **Источники:** HP-01 (host-perf), PH-02 (host-python), CV-C1 (cross-verify, независимо), host-go.
* **Модуль / класс:** HOST.md §1.3 («условия по данным той же версии, что и снимок») + §2 (отдельный асинхронный
  исполнитель outbox). PRODUCT (контракт).
* **Путь:** любой хост, сделанный по HOST.md, если условие зависит от эффекта `call` — это канонический паттерн
  самого примера (`add_to_cart` → `cart_not_empty`).
* **Последствие:** pizza: «Добавить», затем «Оформить» → `cart_not_empty=false` → `catalog` вместо `address`;
  бот с балансом: двойное нажатие «Купить» → 2 товара на баланс одного (−100); общий FIFO-исполнитель и медленная
  CRM соседа → 20 из 20 пользователей уходят не туда.
* **Вероятность:** высокая (двойные нажатия, любая очередь исполнителя).
* **Повтор:** `agents/host-perf/REPRODUCTIONS/host_h1_guard_before_call.sh`;
  cross-verify `xverify/c1_guard_before_outbox.py <ENGINE> examples/pizza.bot.json <SCR>` (код 0 = эффект
  воспроизведён, bin и fresh; `agents/cross-verify/LOGS/c1-*`).
* **Почему проект не заметил:** `host_sim.py` возвращает `true` для всех условий (I-08 / HP-07).
* **Исправление:** HOST §1.3 (host-perf c8bb903 → integration **8fdcb4b**): барьер на пользователя (дождаться его
  незавершённых `call`) или исполнение меняющих данные `call` в транзакции снимка; условия получают данные события.
  `host_sim.py` переписан: условия из данных, ложные ветки, барьер.
* **Регрессионный тест:** `host_sim.py --no-barrier` — красный 10/10, с барьером — зелёный 30/30 (`agents/integration/LOGS/64-*`).

### P-03. Накопительное подтверждение getUpdates теряет обновление
* **Источники:** HP-03 (host-perf, модель), CV-C2 (cross-verify, модель; семантика Telegram сверена с docstring
  python-telegram-bot 21.6 из зеркала PyPI — живой Bot API недоступен).
* **Модуль:** HOST §1.1 (пользователи параллельно) + §1.5 (подтверждать после фиксации).
* **Последствие:** A (`payment:success`) ещё обрабатывается, B зафиксирован и подтверждён `offset` → сбой → A
  больше не придёт: оплата есть, заказа нет. Webhook-хосты не затронуты. Отмечено также: `Updater`
  python-telegram-bot подтверждает пакет до обработки — на нём §1.5 в режиме polling невыполним.
* **Оценка:** host-perf — P1, cross-verify — P2 (нужен getUpdates + параллельность + узкое окно сбоя). Итог: P1 для
  getUpdates-ботов с платежами, P2 в общем случае. LIKELY.
* **Исправление:** HOST §1.5 (8fdcb4b): webhook — 2xx после фиксации; getUpdates — входящая очередь в БД или `offset`
  только до наименьшего незавершённого `update_id`.

## P2

### P-04. Таймер старой версии документа запускает переходы (CC-01 = ET-02)
* **Источники:** CC-01 (core-compiler, случайным поиском без подделки снимков — 30 расхождений на 400 документах
  с обновлением, сжато до 135 байт), ET-02 (engine-timers), PH-07 (host-python), NP-05 (host-go), HP h3f (host-perf).
* **Механизм:** при уходе с сообщения отменяются только таймеры, которые ему приписывает **новый** документ; таймер,
  запущенный по старому, остаётся в `snapshot.timers` навсегда, а его срабатывание с верным жетоном принимается и
  может запустить стрелку раздела/корня или чужого сообщения — включая `call`. Доказательство `compile_correct` этого
  не видит: Core и Chart делят логику выхода и приёма жетона.
* **Повтор:** `agents/core-compiler/REPRODUCTIONS/H2_stale_timer_after_upgrade/repro.py` (код 1 = воспроизведено),
  `H2_min_shrunk/repro.sh`; `agents/engine-timers/REPRODUCTIONS/repro.py f2-moved-timer|f3-renamed-timer`.
* **Исправление (integration d3782f7, VERIFIED-WITH-NOTES):** при выходе отменять и таймеры снимка, которых не
  отменяет `exit` (`staleCancels`, пусто в пределах одной версии); принимать срабатывание только на сообщении-владельце
  (`ownsTimer`); то же правило в `Engine.missing`/`Trace`. Два доказательства восстановлены без изменения
  формулировок; 601 теорема — стандартные аксиомы; leanchecker — ok. Регресс: directed H2, U4h/U5h — FAIL → PASS;
  независимый оракул с исправленной семантикой — 0 расхождений на 496 975 запросах; в пределах одной версии поведение
  не изменилось (golden, conformance 18 103, 100 документов, 107/107 мутаций). **`bin/` не пересобран** (INT-01).

### P-05. Устаревший снимок и откат БД переиспользуют `seq`
* **Источники:** ET-03, HP-02 h2c (откат БД → **второй** заказ), PH-08 (trust-snapshot: коллизия ключа, тупик `seq_overflow`).
* **Исправление:** 7730517 — `restart` только с последним зафиксированным снимком, верхняя отметка `seq` у хоста.
  Остаток: если отметка хранится в той же базе, которую откатывают (failover с RPO>0, восстановление из бэкапа), h2c
  остаётся; рекомендуемый ключ — `пользователь:update_id:действие:вхождение` или эпоха.

### P-06. Сверхлинейная загрузка документа, двойная компиляция
* **Источники:** CC-02 (core-compiler), HP-10 (host-perf), CV-C6 (cross-verify, PARTIALLY: показатели ниже, порядок тот же).
* **Причины:** `rows` = каждое сообщение × каждое событие документа через `cands`/`anc` с линейным `find` и
  фильтрацией всех стрелок; `histCands` фильтрует все сообщения на раздел; `lint` квадратичен и сам вызывает
  `compile.wf`, после чего `Engine.load` компилирует ещё раз (load ≈ 1,6–2,1 × check).
* **Замеры** (общая машина, порядок величин надёжнее абсолютов): общие события 2000 сообщений — 2,2–8,3 с, 3000 —
  22 с CPU; уникальные кнопки 1000 сообщений — 49–221 с, 2000 — не загрузился за 300 с; 100 разделов × 20 с
  «вернуться» — 33,5 с, 200 × 20 — >300 с; вложенность 100 уровней, 500 сообщений — 93 с; `figram random 1000` — 65 с CPU.
  README «1000 сообщений — 1 с» верно только для одного раздела с одной общей стрелкой.
* **Последствие:** каждая загрузка процесса движка, каждая замена процесса после сбоя (HOST §5), каждое обновление
  документа; вместе с таймаутом клиента (I-01) — постоянная недоступность.
* **Предложение:** индексы (узел → предки, (узел, событие) → стрелки), события только предков, одна компиляция,
  `wf` по множеству; для доказательств — быстрая реализация + теорема равенства спецификационной.

### P-09. Abort при ограничении адресного пространства (FFI-10 = NP-01 = ET-10)
* `figram_init` при `RLIMIT_AS` ≤ 1,5 ГБ (ffi-go) / ≤ 3 ГБ (host-go, в процессе Go) — `lean::exception: failed to
  create thread` → `std::terminate` → SIGABRT всего хоста; `figram-engine` при 3 ГБ — rc −6. Встраивание добавляет
  ≈2,2 ГБ VSZ, поэтому лимит, безвредный для обычного сервиса, становится смертельным. Предложение: C++-обёртка с
  `catch(...)` → код ошибки; ленивый старт цикла libuv; документировать требования.

### P-10. Стоимость текстового разбора (FS-1/2/3, ET-08, FFI-13, X1, корень C4)
* Проверка дублей ключа `acc.any` — O(N²) на объект: 16 тыс. ключей — 1 с, 32 тыс. — 4,5 с, 40 тыс. в `guards` —
  7,5 с, `resume` из 50 тыс. записей — 10,4 с, 100 тыс. — 48 с. Накопление числа по цифрам — O(n²): 160 тыс. цифр —
  2–10 с. Память ≈ 40–50 × размер входа (`String.toList`): 20 МБ строка — ≈1 ГБ RSS, 50 МБ — «INTERNAL PANIC: out of
  memory», процесс движка погибает; во встроенном варианте гибнет хост.
* **Достижимость:** строка запроса строится хостом; вход Telegram ограничен (текст ≤ 4096 символов, callback ≤ 64 байт),
  поэтому внешний пользователь напрямую до этого не дотягивается; опасны испорченный/подделанный снимок в БД и ошибки
  хоста. Процесс движка однопоточный: один такой запрос блокирует всех пользователей процесса (см. I-04).
* **Предложение:** множество ключей вместо линейного поиска, предел числа цифр, предел размера запроса в движке и FFI.

## P3 (кратко; детали — в отчётах агентов)
