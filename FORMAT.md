# Формат документа Figram, версия 1

Документ — это то, что редактор отдаёт разработчику: весь бот одним JSON.
Ниже формат выведен из явных критериев. Каждое решение либо следует из
критерия, либо выбрано между равноценными вариантами, и тогда это сказано.
Свойства, отмеченные «доказано», проверены в Lean (`Figram/FormatProofs.lean`).

## 1. Постановка

**Модель** `M` — множество документов: дерево разделов и сообщений,
стрелки с упорядоченными вариантами, условия, действия и переменные
с текстовыми описаниями, напоминания. В Lean это тип `Format.Doc`.

**Формат** — пара функций: запись `enc : M → JSON` и чтение
`dec : JSON → M ∪ {ошибка}`.

**Каноническая форма** — образ `enc`: тот JSON, который пишет редактор.
Читатель обязан принимать и неканонические записи того же документа
(другой порядок ключей, явные значения по умолчанию).

## 2. Критерии

**К1. Полнота и точность.** `dec(enc(d)) = d` для любого корректного `d`.
Ничего не теряется, включая неизвестные ключи и их порядок. *Доказано:*
`decode_encode`.

**К2. Однозначность.** Разные документы записываются по-разному:
`enc` инъективна. *Доказано:* `encode_injective` (следствие К1).

**К3. Минимальность.**
(а) В JSON нет данных, которые вычисляются из остальных.
(б) Значения по умолчанию в канонической форме не пишутся.
(в) У документа ровно одна каноническая запись. Документ здесь — упорядоченная
структура: порядок ключей в словарях (`children`, `on`, `conditions` и т. д.)
сохраняется, чтобы не терять порядок, в котором работает дизайнер. Поэтому два
документа, отличающиеся только порядком ключей словаря, ведут себя одинаково,
но записываются по-разному. Для хешей и сравнения «по смыслу» словари нужно
дополнительно упорядочить по ключу; `figram fmt` этого не делает.

**К4. Структурная корректность.** Пусть `V` — условия корректности, которые
структура JSON не обеспечивает и которые приходится проверять отдельно.
Формат выбирается так, чтобы `V` было минимальным: всё, что можно сделать
невозможным самой формой данных, делается невозможным.

**К5. Расширяемость.**
(а) Неизвестные ключи читаются, сохраняются и не влияют на поведение бота.
*Доказано:* `toChart_strip`, сохранение — частный случай К1.
(б) Расширение, меняющее смысл, объявляется в `requires`; читатель, который
его не знает, отвергает документ целиком, а не читает его неправильно.
*Доказано:* `decode_requires`.
(в) Новое поле имеет значение по умолчанию, равное прежнему поведению,
поэтому старые документы для нового читателя значат то же самое.

## 3. Вывод

Каждая строка — решение, отвергнутая альтернатива и то, что решение даёт
по критериям. Число в последнем столбце — сколько условий из `V`
устранено по сравнению с альтернативой.

| № | Решение | Альтернатива | Что даёт | −V |
|---|---|---|---|---|
| 1 | Вложенные узлы: раздел содержит `children` | Плоский список узлов со ссылкой `parent` | Дерево по построению: нет циклов, у узла ровно один родитель, родитель существует и это раздел | 4 |
| 2 | Узлы — объект «имя → узел» | Массив узлов с полем `id` | Имена соседей уникальны по построению; нет поля `id` (К3а) | 1 |
| 3 | Бот — корневой раздел `bot` | Поле `root` со ссылкой на узел | Нет условия «корень существует»; глобальные команды вроде `/start` — обычные стрелки корня | 1 |
| 4 | Стрелки внутри узла: `on` — объект «событие → варианты» | Отдельный список стрелок с полем `src` | Нет условия «источник существует»; у пары «узел, событие» одно место, поэтому порядок вариантов однозначен (К3в) | 2 |
| 5 | Массив только там, где порядок — смысл: варианты стрелки и действия | Массивы повсюду | Остальные коллекции — объекты, без условий уникальности и без ложного порядка (К3в) | — |
| 6 | Цель — одно поле `to`, «вернуться туда, где был» — признак `resume` | Два поля `to` и `back` | Ровно одна цель по построению: нельзя указать обе или ни одной | 1 |
| 7 | Вид узла определяется наличием `children` | Поле `kind` | Нет поля, которое вычисляется из остальных (К3а), и нет рассогласования «kind: message, но есть children» | 1 |
| 8 | Одно условие на вариант: `"if": "имя"` | Список условий | Дизайнер пишет условие текстом, а текст может сказать «A и B»; список был бы вторым способом записать то же (К3в) | — |
| 9 | Тексты условий, действий и переменных — в словарях `conditions`, `calls`, `variables`; в стрелках только имена | Текст прямо в стрелке | Текст пишется один раз, даже если условие стоит на десяти стрелках; разные тексты одного условия невозможны | 1 |
| 10 | Напоминания внутри сообщения: `timers` | Отдельный список таймеров с полем `node` | Таймер не может указывать на несуществующий узел; на разделе запрещён схемой | 2 |
| 11 | Значения по умолчанию не пишутся: `on`, `timers`, `if`, `resume: false`, `do`, `requires`, словари | Все поля всегда | К3б; читатель принимает и явную запись умолчания | — |
| 12 | Число в модели — точное `m · 10^e`; поля формата проверяются по значению | Только целые | Расширения могут хранить любые числа (координаты, масштаб); `7200000`, `7.2e6` и `7200000.0` — одна задержка | — |

**Числа.** Грамматика числа — RFC 8259; модуль показателя степени в тексте
не больше 1000 (защита от входов вроде `1e1000000000`). Целые поля формата
(задержки таймеров) — от 0 до 2^53 − 1: такое число точно представляют
JavaScript, Go, Rust и Python. Числа с большим отрицательным показателем
печатаются в научной записи, пока модуль показателя не больше 1000; при
меньшем показателе (он бывает только у чисел с дробной частью, например
`1.0e-1000`) — позиционно, чтобы напечатанное читалось обратно. Отрицательный
ноль модель не различает: `-0.0` записывается как `0.0`.

### Что остаётся в `V` и почему меньше нельзя

После решений 1–12 смысловых условий пять, и именно их проверяет `figram check`:

- **V1.** Имена узлов уникальны во всём дереве и непусты.
- **V2.** `initial` раздела — его прямой потомок.
- **V3.** Каждое `to` существует; при `resume: true` это раздел.
- **V4.** Каждое `if` описано в `conditions`, каждое `do` — в `calls`.
- **V5.** Событие `timer:<имя>` ссылается на существующий таймер.

Кроме них `check` проверяет то, что в тексте JSON выполняется само собой, но
может нарушиться у документа, собранного программно: имена в словарях непусты
и не повторяются, аннотации не совпадают с ключами формата. Поэтому документ,
прошедший `check`, гарантированно записывается в модель JSON `J` и читается
обратно (теорема `check_roundtrip`); круг через текст (`print`/`parse`) не
доказан и проверяется тестами.

V1 и V3–V5 — ссылки между частями документа. Значение JSON — конечное
дерево, а граф стрелок бота содержит циклы (меню → заказ → «Отмена» → меню).
Значит, стрелки нельзя записать вложенностью, их приходится записывать
именами, а у любой ссылки по имени есть условие «имя существует и
однозначно». Поэтому V1, V3, V4 и V5 неустранимы ни в каком формате на JSON.

V2 можно было бы устранить, сделав начальным первый узел раздела. Но тогда
порядок `children` стал бы смыслом, детей пришлось бы хранить массивом
с полем имени, и вернулось бы условие уникальности имён среди соседей.
Это обмен одного условия на другое, а не выигрыш; выбран вариант, в котором
все коллекции узлов — объекты.

## 4. Грамматика

```
Документ  = { "figram": 1,
              "requires"?:   [Имя],
              "conditions"?: { Имя: Текст },
              "calls"?:      { Имя: Текст },
              "variables"?:  { Имя: Текст },
              "bot":         Раздел,
              …аннотации }

Узел      = Раздел | Сообщение                  (Раздел ⇔ есть "children")

Раздел    = { "initial": Имя,
              "on"?:       Стрелки,
              "children":  { Имя: Узел },
              …аннотации }

Сообщение = { "on"?:     Стрелки,
              "timers"?: { Имя: Целое 0 … 2^53−1 },  (задержка в миллисекундах)
              …аннотации }

Стрелки   = { Событие: [Вариант] }               (первый подходящий выигрывает)

Вариант   = { "if"?:     Имя,                    (нет — «иначе / всегда»)
              "to":      Имя,
              "resume"?: true,                   (вернуться туда, где был)
              "do"?:     [Имя],
              …аннотации }
```

Машиночитаемая версия структурной части — `figram.schema.json`
(JSON Schema 2020-12).

Все имена (узлов, событий, таймеров, условий, действий, переменных) непусты
и не повторяются в своём словаре.

Срабатывание напоминания приходит событием `timer:<имя>`; префикс `timer:`
зарезервирован. Остальные имена событий формат не ограничивает; редактор
использует соглашение `btn:…`, `cmd:…`, `msg:…`, `payment:…`.

Пример — `examples/pizza.bot.json`.

## 5. Правила расширения

**Аннотации** — всё, что не меняет поведение автомата: координаты на холсте,
тексты сообщений, подписи кнопок, комментарии. Пишутся в ключах с префиксом
`x-` (`x-ui`, `x-content`, `x-note`) в объектах с фиксированными ключами:
документ, раздел, сообщение, вариант. В словарях (`children`, `on`, `timers`,
описания) ключи — это имена, поэтому аннотаций там нет. Ключи формата никогда
не начинаются с `x-`, поэтому аннотации не столкнутся с будущими полями формата.
Читатель, который переписывает документ, обязан сохранять все неизвестные
ключи. Пример — `examples/annotations.bot.json`.

**Смысловое расширение** — новое поле или новое значение, которое меняет
поведение бота. Добавляется так:

1. У расширения есть имя, например `section-timers` (напоминания на разделах).
2. Документ, который его использует, пишет `"requires": ["section-timers"]`.
3. Читатель, не знающий `section-timers`, отвергает такой документ целиком
   (К5б). Без этого правила старый читатель молча проигнорировал бы таймер
   и бот повёл бы себя иначе, чем нарисовал дизайнер.
4. Поведение по умолчанию (поле отсутствует) совпадает с поведением версии 1 (К5в).

**Новая основная версия** (`"figram": 2`) нужна только если изменение нельзя
выразить пунктами выше, например если меняется смысл существующего поля.

## 6. Что доказано, а что нет

| Свойство | Где |
|---|---|
| К1: запись и чтение возвращают тот же документ | `decode_encode` |
| К2: разные документы — разный JSON | `encode_injective` |
| К5а: неизвестные ключи не влияют на поведение | `toChart_strip` |
| К5б: принятый документ требует только известных расширений | `decode_requires` |
| Описания условий, действий, переменных не влияют на поведение | `toChart_decls` |
| Документ, прошедший `check`, записывается в модель `J` и читается обратно | `check_roundtrip` |

Условия теорем (`DocWF`): аннотации не используют ключи формата,
`requires` содержит только известные расширения, `bot` — раздел.
`check` проверяет их в вычислимом виде (`Doc.wfOK`, теорема `wfOK_sound`).

Не покрыты доказательствами:

- текстовый слой (`Figram/FormatIO.lean`): разбор и печать JSON;
  он маленький, отвергает повторяющиеся ключи, ведущие нули и лишние
  запятые, и проверяется тестами;
- соответствие `figram.schema.json` декодеру: проверено на примерах;
- К3 и К4: это свойства вывода выше, а не теоремы.

## 7. Снимок и протокол движка, версия 1

Документ — формат обмена между редактором и разработчиком. Снимок и протокол —
формат обмена между движком и хостом. Плоский автомат, в который компилируется
документ, — внутреннее представление движка и форматом обмена не является:
все движки (процесс `figram-engine`, библиотека для Go) строят его сами из
документа доказанным компилятором.

### Снимок пользователя

То, что хост хранит в базе между событиями:

```
Снимок = { "v"?:      1,                         (версия; нет — 1)
           "at":      Имя,                       (текущее сообщение)
           "resume"?: { Раздел: Сообщение },     (запомненные места)
           "timers"?: { Таймер: Жетон },         (активные таймеры)
           "seq"?:    Целое }                    (номер последнего перехода; нет — 0)
```

Жетоны и `seq` — целые от 0 до 2^53 − 1; имена и значения в `at`, `resume`,
`timers` — непустые строки. Снимок строгий: движок принимает ровно то, что
разрешает `snapshot.schema.json`; неизвестное поле или неизвестная версия —
ошибка (такой снимок записан более новым движком).
`seq` растёт на 1 с каждым переходом; это жетон таймеров, запущенных на этом
переходе, и основа ключей идемпотентности у хоста (HOST.md).

### Протокол

Одна строка JSON на запрос, одна на ответ, с тем же `id`:

| Запрос | Ответ |
|---|---|
| `{"op": "hello"}` | `{"protocol": 1, "states": N}` |
| `{"op": "start"}` | `{"snapshot": …, "actions": […]}` |
| `{"op": "restart", "snapshot": …}` | `{"snapshot": …, "actions": […]}` — начать заново, не сбрасывая счётчик |
| `{"op": "step", "snapshot": …, "event": "btn:x", "guards"?: {…}}` | `{"snapshot": …, "actions": […], "recovered"?: true}` или `{"need": [условия]}` |
| `{"op": "step", …, "event": "timer:<имя>", "token": n}` | как выше |

Действия для хоста, по порядку исполнения:
`{"send": сообщение}`, `{"call": действие}`,
`{"start_timer": имя, "ms": задержка, "token": жетон}`, `{"cancel_timer": имя}`.

Правила шага:
1. Если сообщения из снимка нет в документе — пользователь начинает бота
   заново: отмена всех его таймеров, затем действия первого входа;
   в ответе `"recovered": true`. Запомненные места сохраняются.
2. Событие таймера с жетоном, отличным от текущего, игнорируется:
   снимок не меняется, действий нет.
3. Если варианту стрелки нужны условия, которых нет в `guards`, ответ —
   `{"need": [...]}`; хост вычисляет их по той же версии снимка и повторяет.
4. Событие без подходящей стрелки игнорируется.

5. Если новый `seq` превысил бы 2^53 − 1, ответ — `{"error": "seq_overflow"}`:
   движок не выдаёт снимок, который сам не сможет прочитать. При одном переходе
   в миллисекунду до границы — около 285 000 лет.

`restart` отменяет таймеры снимка, очищает запомненные места и выполняет
действия первого входа, но продолжает счётчик `seq`. Поэтому жетоны новых
таймеров больше любых старых, и запоздавшее событие старого таймера не
совпадёт с новым. Начинать пользователя заново через `start` (счётчик с нуля)
можно только если старых таймеров у него гарантированно нет.

Ошибки запроса — `{"error": "..."}`; снимок при этом не меняется.
